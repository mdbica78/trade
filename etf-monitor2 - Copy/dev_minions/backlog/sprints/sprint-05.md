The sprint's **live** checks need the deployed app with Neon (Sprint 1 live chain) and, for US-024, at least one `job_runs` row written on the deployment (Sprint 3 live chain). Until then the sprint is built and verified offline (PGlite, render tests, mocked `fetch`), and its live steps wait in the QA checklists.

## Goal

Configuration and operational visibility without touching code (roadmap, Sprint 5; EPIC-05 "Done when": "ETFs, tracked fields, AI provider, and cron hour are all manageable without touching code, and job/parse failures are visible").

Concretely: a separate admin area (`/admin`, requirements §5) with forms, not chat, over the same configuration data the Sprint 6 chat will change (FR9 "both paths (chat and form) operate on the same configuration model"). It covers ETF management (FR9), tracked fields per ETF (FR10), the AI provider choice and its API key status (FR11), the cron hour (FR12), and an operational dashboard with cron runs, the last successful extraction per ETF and parse errors (FR13). The admin area stays open, with no login (requirements §6, decided). No chat (Sprint 6). No new extraction adapter (requirements §5: "creating a new extraction adapter … remains development work").

## Why this order

- **US-020 first.** It builds what the rest of the sprint reuses: the `/admin` shell and its header link, the shared configuration-write layer (`lib/config/`) that Sprint 6's chat will call too (FR9), and the pattern for admin reads and writes (`BatchRunner` + PGlite, carry-forward note). It also fixes the seed-overwrite problem (Sprint 1 audit W2). The carry-forward note says to fix it "with or before the first admin story", because once the admin area can change configuration, a `pnpm db:seed` re-run must not undo it.
- **US-021 after US-020.** Tracked fields are per ETF, so it needs US-020's ETF list and config layer. It edits the rows that drive the home-table columns (carry-forward note, Sprint 4 decision 3), so it must prove the home table and the daily job follow the change.
- **US-022 and US-023 after US-020**, in any order, in parallel with US-021. Each is one settings form over one or two `settings` columns. Neither touches another story's code.
- **US-024 last** (it can run in parallel with US-021..US-023 once US-020 is in). It first fixes the Sprint 3 audit N4 outcome-code bug in `lib/ingestion/ingest-etf.ts`, then displays the codes, as the carry-forward note requires ("fix before the dashboard displays these codes").

## Manual QA the user must perform in this sprint

Needs the deployed app with `DATABASE_URL` set. Step 7 needs at least one `job_runs` row on the deployment. The Codex QA loop can check the offline and locally served parts (`scripts/claude/qa-serve.sh`: without `DATABASE_URL`, each admin page shows a translated error, not a crash). Everything below uses your Neon data or your Vercel settings, so it is yours.

1. **Seed is safe to re-run (US-020).** In the Neon SQL editor note `select symbol, name, is_active from etfs; select * from tracked_fields; select * from settings;`. In `/admin`, deactivate one ETF and (after US-021) remove one tracked field. Then run `DATABASE_URL=<neon-url> pnpm db:seed` locally. Re-run the three queries: the deactivated ETF is still inactive, the removed tracked field did not come back, `settings` is unchanged.
2. **ETFs (US-020).** Open `https://<your-app>.vercel.app/admin`. Add a real BVB ETF that is not monitored yet (for example `ICBETNETF`). Expected: it is listed. Its adapter is "none" (no adapter exists for its format, section 3), and the home table shows it with "extraction unavailable". Remove it: it disappears from the home table, and the next daily run does not process it (its symbol is missing from the new `job_runs.log`). Activate it again, or leave it removed.
3. **Tracked fields (US-021).** For `BTBETRETF`, track "Activ net" and move it first. Reload `/`: an "Activ net" column appears. Under P1's literal reading it stays empty until the next daily run. Untrack it again: the column disappears, and its stored values are still in `report_values`.
4. **AI provider (US-022).** In `/admin/ai`, pick a provider and save. In Neon, `select ai_provider, ai_model from settings;` shows it. Set that provider's key variable (the name is shown on the page) in the Vercel project's environment variables and redeploy: the page then shows "set", never the key.
5. **Cron hour (US-023).** In `/admin/cron`, set an hour other than 10 and save. The page shows the notice with the exact `vercel.json` line. Change `vercel.json` accordingly, commit, push and wait for the Production deployment. Vercel → project → Settings → Cron Jobs shows the new schedule, and the admin page no longer shows the notice. The next `job_runs.started_at` falls inside the new hour (UTC).
6. **Dashboard (US-024).** Open `/admin/operations`: the runs from `select * from job_runs order by id desc` are listed with translated status and outcomes, in RO and EN. Each ETF shows its last successful extraction, matching `select etf_id, max(report_date) from reports where status = 'ok' group by etf_id`. Any `parse_error` report is listed with its message and stored values.
7. **PO confirmation:** every story in this sprint was drafted by an agent. Confirm or correct the acceptance criteria, and answer the PRODUCT items above (#4, #5, #6, #8, #9, #11, #14, #15, #16). #9 (API keys) and #11 (cron hour needs a redeploy) are the two that change what FR11/FR12 deliver.
