# US-017 — Day-over-day delta calculation (absolute and percentage)
> Detailed by agent (story-planner), 2026-09-25 — PO to confirm at demo.

**Sprint:** 4 · **Epic:** EPIC-04 · **Depends on:** US-016
**Suggested model / thinking:** mid model, medium thinking. Complex (exact decimal arithmetic, a date rule, 8 ACs), so it is planned by `story-planner`.

## Context

FR7: for each parameter the home table shows "today's value + the difference vs. the previous day (both absolute and percentage)". US-016 shows the value from the ETF's newest `ok` report, with that report's date (US-016 decisions 1 and 2). This story adds the two differences.

Two things make this more than a subtraction:

- **Exactness.** `report_values.numeric_value` is a Postgres `numeric` and reaches the app as a canonical decimal string (`11.091`, `8640000.00`). JavaScript floating point turns `11.091 - 11.085` into `0.005999999999999339`, and `(0.015).toFixed(2)` gives `"0.01"`. A displayed delta must be the true difference, not a float artefact.
- **"Previous day".** Stored report dates have gaps. Under US-012 PRODUCT 2's literal reading (still open for the PO), the Monday filing holds the Friday, Saturday and Sunday reports, and only Sunday's is stored (`test/fixtures/bvb/README.md` §2). Sprint 3's forward note asks this story to define "previous day" (decision 1).

## Task

1. **Pure delta module**, e.g. `lib/monitoring/delta.ts`, with no I/O:
   - `previousCalendarDay(isoDate)`: the date-only string for the day before (`2026-03-01` → `2026-02-28`). Pure calendar arithmetic, no time zone, no local `Date` parsing;
   - `computeDelta(current: string, previous: string)`: returns `{ absolute: string, percent: string | null }`, both canonical decimal strings, computed exactly (e.g. scaled `BigInt` arithmetic on the decimal strings):
     - `absolute = current − previous`, with as many decimals as the more precise of the two inputs;
     - `percent = (current − previous) / |previous| × 100`, rounded to 2 decimals, half away from zero (decision 2); `null` when `previous` is zero.
2. **Read model**: extend US-016's home view model. For each row with a `valueDate`, load the ETF's `ok` report for the calendar day before `valueDate` (decision 1), and add to each tracked cell `delta: { absolute, percent } | null`. `delta` is `null` when the current value is `null`, when there is no `ok` report for that day, or when that report has no value for the field.
3. **Display**: `formatDelta` (or an extension of `formatNumber`) renders the sign and the DEC-007 decimal mark: `+0,006` / `+0,05%` in `ro`, `-30000` / `-0.08%` in `en`. Zero shows no sign. `%` follows the number with no space. The home-table cell shows the value, then the absolute delta, then the percentage. A `null` delta renders nothing; it is never shown as `0`.
4. **Messages**: any new label (for example an accessible label or column sub-heading for the two deltas) goes into both catalogues.
5. **Tests**: pure unit tests for `previousCalendarDay`, `computeDelta` and the formatter; PGlite tests for the read model; render tests of the table in `ro` and `en`.

## Acceptance criteria

- **AC1** — The absolute delta is exact. `computeDelta` unit tests:
  - `11.091` vs `11.085` → `0.006`;
  - `37470000` vs `37500000` → `-30000`;
  - `8640000.00` vs `8639999.5` → `0.50` (precision of the more precise input);
  - `11.091` vs `11.091` → `0.000`.

  No test result depends on floating-point rounding. (FR7 "difference … absolute"; data model `report_values.numeric_value` `numeric`; AGENTS.md "Never guess a value")
- **AC2** — The percentage is exact and rounded as decision 2 says:
  - `11.091` vs `11.085` → `0.05`;
  - `37470000` vs `37500000` → `-0.08`;
  - `1000.15` vs `1000` → `0.02` (exactly 0.015, rounded half away from zero; `toFixed` on a float gives `0.01`);
  - `999.85` vs `1000` → `-0.02`;
  - any value vs `0` → `null`, while the absolute delta is still returned.

  (FR7 "difference … percentage"; decision 2)
- **AC3** — "Previous day" is the calendar day before the shown report's date (decision 1). `previousCalendarDay` unit tests: `2026-09-22` → `2026-09-21`; `2026-03-01` → `2026-02-28`; `2028-03-01` → `2028-02-29`; `2027-01-01` → `2026-12-31`. The result does not depend on the process time zone. The read model applies the same rule: if it computes the previous day in SQL (for example `report_date - 1`) rather than through `previousCalendarDay`, a PGlite test proves the month and year boundaries (`2026-03-01` → `2026-02-28`, `2027-01-01` → `2026-12-31`) through the read model itself. (FR7 "vs. the previous day"; data model `reports.report_date` "the date the report is **for**")
- **AC4** — Blank, never guessed. PGlite tests: the delta is `null` when:
  - there is no report for the previous calendar day, even if an older `ok` report exists (for example 2026-09-20 and 2026-09-22 stored, 2026-09-21 missing);
  - the previous day's report is `parse_error`, even with a stored value for the field (US-016 decision 2);
  - the previous day's `ok` report has no value for the field;
  - the current value is `null`.

  With `ok` reports on two consecutive days, the delta is the exact difference of the two stored values. (FR4.1 "that day remains blank … (no value)"; AGENTS.md "Never guess a value"; decision 1)
- **AC5** — Display. Deltas render with an explicit sign (`+`/`-`, none for zero), the locale's decimal mark and no grouping (DEC-007), and `%` after the percentage with no space: `ro` `+0,006` and `+0,05%`; `en` `-30000` and `-0.08%`; zero `0,000` and `0,00%` in `ro`. The sign follows the displayed, rounded value: a non-zero change whose percentage rounds to zero shows `0,00%`, never `-0,00%` or `+0,00%`. (DEC-007; FR7; decision 2)
- **AC6** — Home table. Every tracked cell with a value shows the value, the absolute delta and the percentage delta. A `null` delta renders no text, not `0`. Render tests in `ro` and `en` cover a cell with both deltas, a cell with only an absolute delta (previous value 0), and a cell with no delta. Every new string is in both catalogues, and the key-parity test passes. (FR7; FR8.1; AGENTS.md "Every UI string goes through next-intl")
- **AC7** — Offline. The read-model tests run on PGlite with the shipped statements. No test connects to Neon. (AGENTS.md "Tests never call live Neon")
- **AC8** — `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. (AGENTS.md Commands)

## Out of scope

- Deltas on the detail page, in its history table or its charts (FR8 asks for historical values, not deltas).
- Colour coding, arrows or thresholds for "significant" changes (section 6: notifications and the AI news feed are out of scope).
- Comparing against an older stored report when the previous day is missing (decision 1, option B, only if the PO picks it).
- Any database write or schema change.

## Decisions needed

1. **PRODUCT — what is "the previous day"?** (non-blocking; sprint-03.md forward note)
   - A: the `ok` report for the calendar day before the shown report's date. If there is none, the delta is blank. **This story implements it.** It is the literal FR7 reading and matches FR4.1 ("blank"). Under US-012 PRODUCT 2's literal reading, the delta of the Sunday report is blank every week, because Saturday is never stored. That is one day a week.
   - B: the previous **stored** `ok` report, whatever its date. A Sunday report would be compared with Thursday's, shown as a "day-over-day" change that spans three days.
   - Recommendation: **A**. If the PO picks catch-up option B in US-012 (ingest every link of the newest filing), every calendar day has a report and option A is never blank on a normal week. If the PO picks B here, only `previousCalendarDay` and the read query change.
2. **PRODUCT — delta display.** (non-blocking) FR7 does not say how the difference is shown.
   - A: percentage rounded to 2 decimals, half away from zero. Explicit `+`/`-` sign on both deltas, none for zero. `%` right after the number in both locales. Absolute delta with the precision of the more precise input. A zero previous value gives a blank percentage. No colour. **This story implements it.**
   - B: another precision or rounding rule, or colour (green/red).
   - Recommendation: **A**. It keeps DEC-007's "digits as stored" spirit and says nothing the data does not.

## Tech-lead review 2026-09-25

Approved. Two fixes were made in place:

1. **Task 2 asked for something the batch cannot do.** It said to load the previous day's report "in the same batch as the rest of the home query". The previous date depends on `valueDate`, which comes out of that same query. A Neon HTTP `db.batch` cannot feed one statement's result into another, except through SQL itself. The plan now picks one of two options:
   - (a) compute the day in SQL (`report_date - 1` is a `date` in Postgres) inside the home statement;
   - (b) run a second read after the first.

   Both are fine for a read-only page. If the plan picks (a), `previousCalendarDay` would not be on the production path. AC3 now requires a PGlite test to prove the same boundaries through the read model, so a test cannot pass against a helper that the page never calls.
2. **AC5: sign of a rounded-to-zero percentage.** A small change (for example +0.00004 on 1000) rounds to `0.00`. The criterion now says the sign follows the displayed value, so `-0,00%` (a signed zero) can never appear. This applies decision 2's existing "zero shows no sign" rule. It adds no new product choice.
