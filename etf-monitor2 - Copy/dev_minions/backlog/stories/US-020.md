# US-020 — Admin: ETF management (add, remove, activate)
> Detailed by agent (story-planner), 2026-09-26 — PO to confirm at demo.

**Sprint:** 5 · **Epic:** EPIC-05 · **Depends on:** US-003, US-005, US-007, US-008, US-009, US-016
**Suggested model / thinking:** strong model, high thinking. Complex (DB writes, seed rewrite, adapter detection over the Sprint 2 chain, new route group, 11 ACs), so it is planned by `story-planner`.

## Context

Requirements §5 asks for a separate administration area "with structured control (forms, not just natural-language commands) over the same configuration data". FR9: "ETF management: full list of monitored ETFs, manual add/remove (form), independent of the natural-language command — both paths (chat and form) operate on the same configuration model." Section 3: "When a new ETF is added, the system attempts to match it to a known adapter (by issuer/depositary or by report structure). If no adapter matches, the ETF is still shown in the list … but automatic extraction is marked 'unavailable'." FR4.2: a newly added ETF's history "starts empty from that point on — no backfill".

What exists:
- `etfs` (data model): `symbol` UNIQUE, `name` and `bvb_url` NOT NULL, `adapter_key` NULL = no adapter matched, `is_active` = "soft removal from monitoring". The home table (US-016) and the daily job (US-013, `lib/ingestion/load-etfs.ts`) already list only `is_active = true` ETFs.
- The adapter registry (`lib/extraction/adapters/default-registry.ts`) has `get`, `list` and `detect(text)`. `types.ts` documents `detect` as "structure-based matching, used when an ETF has no assigned `adapter_key` yet". The Sprint 2 chain is `discoverLatestReport` → `downloadReportPdf` → `extractPdfText` (`lib/extraction/`).
- Reads and writes go through `db.execute(sql…)` plus an injected `BatchRunner` (`lib/ingestion/store.ts`). PGlite runs the same statements in tests (`test/helpers/pglite.ts`). Carry-forward note: reuse this for admin reads and writes.
- `messages/*.json` already have `Nav.admin` ("Administrare" / "Administration"), unused so far. The header (`components/AppHeader.tsx`) links Home and Health.
- **Seed problem (Sprint 1 audit W2, carry-forward note):** `lib/db/seed.ts` upserts with `onConflictDoUpdate`. A re-run of `pnpm db:seed` resets ETF names and `display_order`, and re-inserts tracked fields the user removed. It also has no test that executes it (Sprint 1 audit W1). The carry-forward says to resolve this "with or before the first admin story". This is that story.

## Task

1. **Seed fix** (sprint decision 1). Rewrite `lib/db/seed.ts` so that:
   - `etfs`, `tracked_fields` and `settings` are inserted only when absent (`on conflict do nothing`). A seeded ETF's tracked fields are inserted only if **this seed run** inserted that ETF, so a field the user removed never comes back;
   - `field_catalog` keeps its upsert (it describes what the adapters, which are code, extract; the admin area does not edit it);
   - the statements run through a `BatchRunner` (`neonBatchRunner` in `scripts/db-seed.ts`, the PGlite runner in tests), so the tests execute the shipped SQL. One batch or several is the plan's call;
   - README "Deployment" says `db:seed` is a first-install bootstrap that is safe to re-run and never overwrites admin changes. In the same edit, fix Sprint 1 audit W5: the "Environment variables" paragraph must not claim the CLI scripts load `.env.local`. They need `DATABASE_URL` exported or inline.
2. **Configuration layer**, `lib/config/etfs.ts` (sprint decision 2). Plain functions, with no Next.js imports, that take a `Db` and a `BatchRunner` and return a typed result instead of throwing on bad input. The Sprint 6 chat will call the same functions (FR9):
   - `listEtfs()`: every ETF (active and inactive), ordered by symbol, with `symbol`, `name`, `adapterKey`, `adapterAvailable` (key set **and** registered, the same rule as US-016 AC5), `isActive`;
   - `addEtf({ symbol, name }, deps)`: validate and normalise the input (decision 5). A new symbol inserts a row with `bvb_url = bvbInstrumentUrl(symbol)`, `is_active = true` and the detected `adapter_key` (step 3). The existing-symbol check comes first, so these two cases make no network request. An existing active symbol → error `already_monitored`, nothing written. An existing inactive symbol → reactivated (decision 4), keeping its stored name and `adapter_key`, with no detection (re-detect is its own action; sprint decision 3). For a new symbol, the result says which adapter, if any, was detected;
   - `setEtfActive(symbol, active)`: soft removal and reactivation (decision 4). Unknown symbol → error `not_found`;
   - `setEtfAdapter(symbol, adapterKey | null)`: only a registered adapter key or null is accepted (sprint decision 3, manual override);
   - `detectEtfAdapter(symbol, deps)`: re-runs detection for an existing ETF and stores the result.
3. **Detection** (sprint decision 3), e.g. `lib/config/detect-adapter.ts`. Given a symbol and its `bvb_url`: one discovery request, at most one PDF download, text extraction, `registry.detect(text)`. Exactly one match → that key. Anything else (not found, fetch error, unreadable text, zero or several matches, a thrown error) → `null` plus a reason code. It never throws, never retries (FR4.1), and **writes nothing** to `reports` or `report_values` (FR4.2). Network, PDF and registry access are injected. The defaults are the Sprint 2 functions with the same timeout the cron uses (`CRON_FETCH_TIMEOUT_MS`).
4. **Admin shell and page:**
   - `app/admin/layout.tsx`: a translated admin heading and a section nav. This story adds the "ETFs" entry, and each later Sprint 5 story adds its own. `/admin` shows the section links. The header (`AppHeader`) gets a `Nav.admin` link to `/admin`. While editing `AppHeader.test.tsx`, also assert the existing `Nav.health` link (Sprint 1 audit N5);
   - `app/admin/etfs/page.tsx`: the ETF list (symbol, name, adapter or a translated "none" / "not registered" marker, active state), an add form, and per-row actions: remove / activate, set adapter (select of registered adapters plus "none"), re-detect;
   - Server Actions in their own file (e.g. `app/admin/etfs/actions.ts`) parse `FormData`, call `lib/config/etfs.ts` with `getDb()`, and return a translated message key. They never return or render an exception's text (AGENTS.md secrets rule, as `app/page.tsx` does). After a successful write, revalidate `/`, `/admin` and `/admin/etfs`;
   - pages read the database per request and are never prerendered with database access.
5. **Messages:** `Admin.*` keys in both catalogues.
6. **Tests:** PGlite tests for the seed and for every `lib/config/etfs.ts` function. Detection tests with mocked `fetch` over the committed fixtures (`test/fixtures/bvb/<SYMBOL>-instrument-2026-09-23.html`, `test/fixtures/<SYMBOL>-2026-09-22.pdf`). `renderToStaticMarkup` tests of the page component in `ro` and `en`. Action tests with the config layer mocked.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1** — Seed is safe to re-run. A PGlite test seeds an empty database, then changes it as the admin would: renames an ETF, deactivates one, deletes a tracked field, changes a `display_order`, sets `settings.default_locale = 'en'`. It then runs the seed statements again. Every one of those changes is still there, and no deleted tracked field is back. A seed on an empty database still produces 3 ETFs, 8 catalogue rows, 6 tracked fields and 1 settings row (US-005 AC). A catalogue label changed in `seed-data.ts` is updated by a re-run. (Sprint 1 audit W1/W2; carry-forward note "Resolve with or before the first admin story"; FR9, FR10)
- **AC2** — List. `/admin/etfs` lists every ETF in the registry, active and inactive, ordered by symbol, with name, adapter (key, or a translated "none" / "not registered" marker) and active state. A PGlite test covers an inactive ETF, a NULL `adapter_key` and an unregistered key. (FR9 "full list of monitored ETFs"; section 3; data model `etfs.adapter_key`)
- **AC3** — Add. `addEtf` with a new valid symbol and a name inserts one `etfs` row: normalised symbol, the name, `bvb_url` from `bvbInstrumentUrl`, `is_active = true`, the detected `adapter_key`. It writes no `tracked_fields`, `reports` or `report_values` row (decision 6; FR4.2). Invalid input (empty or non-alphanumeric symbol, empty name) returns a validation error, writes nothing, and the page shows a translated message. (FR9 "manual add … (form)"; FR1 "any ETF"; FR4.2; decisions 5 and 6)
- **AC4** — Duplicates and reactivation. Adding the symbol of an active ETF returns `already_monitored` and writes nothing. Adding the symbol of an inactive ETF sets it active again and keeps its id, name, `adapter_key`, history and tracked fields, with no network request. The unique key `etfs.symbol` is never violated. (FR9; data model `etfs.symbol` UNIQUE; decision 4)
- **AC5** — Remove and activate. `setEtfActive(symbol, false)` sets `is_active = false` and deletes nothing (its `reports`, `report_values` and `tracked_fields` rows are unchanged). A PGlite test then runs the **shipped** statements of the home-table loader (`lib/monitoring/home.ts`) and of the daily job's loader (`lib/ingestion/load-etfs.ts`): the ETF is absent from both. After `setEtfActive(symbol, true)` it is present in both again. (FR9 "remove"; data model `is_active` "soft removal from monitoring"; FR7 "currently monitored ETFs"; FR3; decision 4)
- **AC6** — Adapter detection. With `fetch` mocked to serve the BTBETRETF instrument-page fixture and `BTBETRETF-2026-09-22.pdf`, detection returns `brd-depositary`. Each of these returns `null` with a reason and never throws: discovery `not_found`, a fetch error, an unreadable PDF, a text that no adapter's `canHandle` accepts, and a registry with two adapters that both accept it. Every case makes at most one discovery request and one download. No test writes a `reports` row, and the detection module takes no store. (Section 3 "attempts to match it to a known adapter … by report structure"; FR4.1 "no automatic retries"; FR4.2; AGENTS.md "Never guess a value"; decision 3)
- **AC7** — Manual adapter override. `setEtfAdapter` accepts a key from `registry.list()` or null, and rejects any other key without writing. Re-detect stores the new detection result, which can be null. (FR9, FR10 "per adapter/report type"; section 3; decision 3)
- **AC8** — Shared configuration layer. `lib/config/etfs.ts` imports nothing from `next/*`, React or `app/`, uses no AI code, and receives its database runner and network functions by injection. The Server Actions contain no SQL; they call it. Checked by a boundary test, like the existing `boundaries.test.ts` files. (FR9 "both paths (chat and form) operate on the same configuration model"; FR5; decision 2)
- **AC9** — Failure states and secrets. When the database read throws, `/admin/etfs` shows a translated error message and no exception text. When a write action's database call throws, the action returns a translated generic error and the response contains neither the exception message nor any environment value. (AGENTS.md secrets rule; FR13 "no silent failure" spirit; US-016 AC9 pattern)
- **AC10** — Bilingual. Every string of the admin shell, the header link and the ETF page goes through next-intl, with keys in both catalogues, and the key-parity test passes. Render tests in `ro` and `en` show the locale's headings, markers and messages, and neither render contains the other locale's differing text. (FR8.1; AGENTS.md "Every UI string goes through next-intl")
- **AC11** — Offline and build-safe. No test connects to Neon or bvb.ro. `pnpm build` passes with `DATABASE_URL` unset. `pnpm typecheck`, `pnpm lint` and `pnpm test` pass. (AGENTS.md "Tests never call live Neon …", Commands; ADR-001)

- A report link for ETFs without an adapter (US-030), a new adapter (requirements §5; US-029).

## Notes for verification

- **Seed and `BatchRunner`.** Today `seed.ts` uses Drizzle's query builder directly, so PGlite cannot run it through the existing helper. Moving it to `db.execute(sql…)` statements run by a `BatchRunner` is how AC1 gets a real test. `test/helpers/pglite.ts` pre-inserts one BTBETRETF row, so the seed test needs an empty database, or a helper option to skip that row. Sprint 3/4 tests must stay green unchanged.
- **"Inserted by this run".** `insert … on conflict do nothing returning id` returns no row for an existing ETF. That is the signal for "do not seed its tracked fields". A plan that re-selects the ETF id afterwards (as today) would re-insert removed tracked fields. AC1 catches it.
- **Detection is not ingestion.** The reviewer checks that the detection path takes no `ReportStore` and that no `reports` row appears in the AC6 tests (FR4.2 "no backfill").
- **Timeouts.** Detection runs inside a Server Action on Vercel. Reusing `CRON_FETCH_TIMEOUT_MS` (7 s per request) keeps the worst case at about 14 s plus text extraction. Server Actions inherit the route segment's `maxDuration`, so the ETF admin route exports `maxDuration = 60` (as `app/api/cron/daily/route.ts` does), and the plan states the action's duration budget against it (sprint decision 3).
- **Symbol format.** Letters and digits only is also what keeps the `job_runs.log` line format (`<SYMBOL> <code> …`, US-015) parseable by US-024.
- Server Actions are public POST endpoints. With no login (requirements §6), anyone who has the URL can use them. Validation in `lib/config/` is the only guard. The reviewer checks that no action accepts a field it does not need.
- **Manual QA (live, user):** sprint-05.md steps 1 and 2.
