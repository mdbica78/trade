# US-006 — Deploy to Vercel with a health-check page

**Sprint:** 1 · **Epic:** EPIC-01 · **Depends on:** US-003 (and US-004 for labels, US-005 for data to display)
**Suggested model / thinking:** mid model, medium thinking

## Context

This story closes Sprint 1 by proving the whole hosting chain works: the app deploys to Vercel's free Hobby plan, reaches Neon Postgres from a serverless function, and renders real data. Everything after this sprint assumes that chain is sound, so it is verified once, explicitly, here.

## Task

1. Build a health-check page at `/health` that performs a real query against the database and reports:
   - database connectivity (success or the error message),
   - the number of ETFs in the registry,
   - the number of entries in the field catalogue,
   - the application's current locale.
   All labels go through translation keys (US-004 convention).
2. Make the page render correctly when the database is unreachable — show a clear failure state rather than throwing an unhandled error. A deployment that cannot reach its database must say so, not return a blank 500.
3. Add `vercel.json` if any configuration is required, and document in the root `README.md`:
   - which environment variables must be set in the Vercel project (`DATABASE_URL`, `CRON_SECRET`),
   - how to run migrations against the Neon database,
   - the deployment steps.
4. Write unit tests for the health-check data function, covering both the success path and the database-unreachable path, using a mocked client. No live database in tests.

## Acceptance criteria

- **AC1** — `/health` renders locally and shows correct counts against a seeded database.
- **AC2** — When the database is unreachable, `/health` renders a clear error state and returns HTTP 200 with a visible failure message (not a 500, not a blank page).
- **AC3** — Labels on `/health` switch between Romanian and English with the language switcher.
- **AC4** — Unit tests cover both the success and failure paths; `pnpm test` passes with no database available.
- **AC5** — The root `README.md` documents the required environment variables, the migration command, and the deployment steps.
- **AC6** — `pnpm build` succeeds.

## Out of scope

- No cron job (Sprint 3), no report ingestion, no monitoring UI.
- Do not add authentication — the application is intentionally open for now (roadmap item).
- Do not create the Vercel project or the Neon database from code, and do not handle any credentials: the user creates those in their own accounts and sets the environment variables themselves.

## Manual steps the user performs (not Copilot)

1. Create the Neon database and copy its connection string.
2. Create the Vercel project from the GitHub repository.
3. Set `DATABASE_URL` and `CRON_SECRET` in the Vercel project settings.
4. Run the migrations and the seed against the Neon database.
5. Open the deployed `/health` URL and confirm it reports a successful connection with the expected counts.
