# US-015 — Job run logging
> Detailed by agent (story-planner), 2026-09-24 — PO to confirm at demo.

**Sprint:** 3 · **Epic:** EPIC-03 · **Depends on:** US-013, US-014
**Suggested model / thinking:** mid model, medium thinking. Complex (cron, DB writes, 10 ACs), so it is planned by `story-planner`.

## Context

FR13 asks for operational visibility: a "history of cron runs (success/failure), last successful extraction per ETF, parsing errors". EPIC-03 covers FR13's job-run log. The data model already has the table:

| column | notes |
|---|---|
| `started_at` | timestamptz NOT NULL |
| `finished_at` | NULL until the run ends |
| `status` | `running` \| `success` \| `partial` \| `failed` |
| `etfs_processed`, `errors_count` | int, default 0 |
| `log` | "human-readable summary" |

US-013 runs the daily job and returns a per-ETF summary. US-014 gives every ETF a stable outcome code (`ok`, `already_ingested`, `missing`, `fetch_error`, `no_adapter`, `parse_error`, `persist_error`). This story records each run in `job_runs`, so that a run that failed, or one that never finished, is visible in the database. The admin dashboard that displays these rows is US-024 (Sprint 5).

## Task

1. **Job-run store**, e.g. `lib/ingestion/job-runs.ts`, behind an injected interface like US-012's store:
   - `startRun(startedAt)` inserts `status = 'running'` and returns the id;
   - `finishRun(id, { finishedAt, status, etfsProcessed, errorsCount, log })`;
   - `failStaleRuns(olderThan)` (step 4).
2. **Wire it into the daily run** (US-013's `runDailyIngestion` or its handler), after auth succeeds:
   1. `failStaleRuns`;
   2. `startRun`. If this or `failStaleRuns` fails (e.g. the database is unreachable), process no ETF and return `500`;
   3. load the active ETFs and run each one (US-013);
   4. `finishRun` with the computed status, counts and log.

   If anything throws after `startRun`, including the ETF query, still call `finishRun` with `status = 'failed'` and the error in the log. The response then reports the failure (`500`).
3. **Status and counts:**
   - `etfs_processed` = the number of active ETFs `ingestEtf` was called for;
   - `errors_count` = the number of those ETFs whose outcome is anything other than `ok` or `already_ingested`: `missing`, `fetch_error`, `no_adapter`, `parse_error`, `persist_error`, the runner's `internal_error` (US-013, a thrown `ingestEtf`), and any code added later. Count by exclusion from the success set, so a new failure code can never be counted as success;
   - `status`:
     - `success` when `errors_count = 0`, including a run with zero active ETFs;
     - `partial` when `0 < errors_count < etfs_processed`;
     - `failed` when every processed ETF failed (`errors_count = etfs_processed > 0`), or when the run aborted (step 2).
4. **Stale runs.** A run killed by the platform's duration limit never reaches `finishRun` and would stay `running` forever, which is a silent failure. At the start of each run, set every row still `running` whose `started_at` is older than a threshold to `status = 'failed'` and append `did not finish (timed out or crashed)` to its `log`. Leave `finished_at` NULL: nobody knows when it ended. The threshold must be longer than the route's `maxDuration` (US-013), e.g. 15 minutes. Keep it in one named constant.
5. **Log format** (`job_runs.log`):
   - line 1 is a summary: `<status>: <etfs_processed> processed, <errors_count> errors`;
   - then one line per processed ETF, in processing order: `<SYMBOL> <outcome_code> <detail>`, where the detail includes the `reportDate` when known;
   - each detail is truncated to a fixed maximum length (e.g. 300 characters);
   - the log never contains `CRON_SECRET`, `DATABASE_URL` or any other environment value;
   - it is plain English diagnostic text. The **codes** are the stable, translatable part (FR8.1): US-024 maps them to next-intl labels and shows the detail as-is.
6. **Response.** The route's JSON summary (US-013) also includes the job run id and its final status.
7. **Tests**: a fake job-run store, a fake loader, and fake `ingestEtf` outcomes. No Neon.

## Acceptance criteria

- **AC1** — Every authorized run writes one `job_runs` row. It is inserted with `status = 'running'` and `started_at` before the first ETF is processed. It is finished with `finished_at`, the final `status`, `etfs_processed`, `errors_count` and `log`. An unauthorized request (`401`, US-013) writes no row. (FR13 "history of cron runs"; data model `job_runs`)
- **AC2** — Status and counts follow Task 3. One test per case:
  - all `ok` → `success`;
  - all `already_ingested` → `success`;
  - zero active ETFs → `success` with 0/0;
  - a mix of `ok` and failures → `partial`;
  - all failures → `failed`.

  Each case asserts `etfs_processed` and `errors_count`. (FR13 "success/failure"; data model `job_runs.status`)
- **AC3** — Each failure code (`missing`, `fetch_error`, `no_adapter`, `parse_error`, `persist_error`, `internal_error`) is counted in `errors_count`, and `ok` / `already_ingested` are not. An unrecognised code also counts as an error. (FR13 "parsing errors (especially useful for ETFs without a matching adapter)"; section 5 "flags that an adapter is missing"; FR4.1)
- **AC4** — The log follows Task 5: a summary line, then one line per ETF with symbol, outcome code and detail (including the report date when known), and details truncated to the fixed maximum. A test with the secret and database URL set in the environment asserts that neither value appears in the log or in the response. (FR13; FR8.1 via stable codes; AGENTS.md secrets rule)
- **AC5** — Abort handling. When the ETF query or the runner throws after the row was created, the row is still finished with `status = 'failed'` and the error message in its log, and the route returns `500`. When `failStaleRuns` or `startRun` itself fails, no ETF is processed and the route returns `500`. (FR13; EPIC-03 "failures are visible rather than silent")
- **AC6** — Stale runs. At the start of a run:
  - rows still `running` and older than the threshold become `failed`, with `did not finish` appended to their log and `finished_at` left NULL;
  - a `running` row younger than the threshold is left untouched;
  - the threshold is a named constant, larger than the route's `maxDuration`, and a test asserts that relation.

  (FR13; data model `job_runs.finished_at` nullable)
- **AC7** — The route's `200` and `500` JSON responses include the job run id (when one was created) and its final status. (FR13)
- **AC8** — All tests run offline with fake stores. No test connects to Neon or makes a network request. (AGENTS.md "Tests never call live Neon …")
- **AC9** — **MANUAL-QA** (sprint-03.md steps 4–6). After a manual trigger on the deployment, `select * from job_runs order by id desc limit 5;` in Neon shows a finished row with correct counts and a per-ETF log. A second trigger the same day shows `success` with `already_ingested` lines. After the next scheduled time, a new row exists without any manual action. (FR13; EPIC-03 "Done when")
- **AC10** — `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. (AGENTS.md Commands)

## Out of scope

- Showing runs, last successful extraction or parse errors in the UI (US-024, Sprint 5).
- A structured per-run, per-ETF table (US-014 decision 1, option C; only if US-024 needs it).
- Alerts or notifications on a failed run (FR4.1; section 6 "Notifications/alerts — none for now").
- Pruning old `job_runs` rows. One row per day is far inside the Neon free tier (data model notes).

## Notes for verification

- **Counting `no_adapter` as an error** makes every run `partial` while an active ETF has no adapter. That is intended: it is the visible flag FR13 and section 5 ask for. It lasts until an adapter exists (US-029) or the ETF is deactivated.
- **`missing` counts as an error, but it is not an alert.** FR4.1 forbids alerts and retries, not bookkeeping. Weekends normally give `already_ingested`, not `missing`, because the last filing stays on the page (`test/fixtures/bvb/README.md` §2).
- **A database outage** makes `startRun` fail, so nothing can be recorded in the database. The `500` response and Vercel's function log are the only trace. That is acceptable and is stated in the QA file.
- The stale-run sweep and the new run are separate statements. Two overlapping manual triggers could both sweep. That is harmless, because the sweep only touches rows older than the threshold.
- `started_at` / `finished_at` are timestamptz. Nothing is displayed in this story, so no timezone formatting is needed yet (Sprint 1 audit N2 applies from Sprint 4).
