# US-003 — Database schema and Drizzle/Neon setup

**Sprint:** 1 · **Epic:** EPIC-01 · **Depends on:** US-002
**Suggested model / thinking:** mid model, medium thinking

## Context

The application stores one row per ETF per field per day, plus configuration and job-run bookkeeping. The full schema is specified in `dev_minions/architecture/data-model.md` — that document is the source of truth for this story; implement it exactly, including constraints.

## Task

1. Add Drizzle ORM and `@neondatabase/serverless`, configured against `DATABASE_URL`.
2. Define the schema in `lib/db/schema.ts`, covering all seven tables from `data-model.md`: `etfs`, `field_catalog`, `tracked_fields`, `reports`, `report_values`, `job_runs`, `settings`.
3. Reproduce every constraint from that document — primary keys, `UNIQUE` constraints, `NOT NULL`, defaults, foreign keys with `ON DELETE CASCADE`, and the `CHECK (id = 1)` on `settings`.
4. Configure Drizzle Kit for SQL migrations, output to `drizzle/`, with `pnpm db:generate` and `pnpm db:migrate` scripts.
5. Generate the initial migration and commit the generated SQL.
6. Create `lib/db/index.ts` exporting a configured database client, reading `DATABASE_URL` from the environment and failing loudly with a clear message if it is absent.
7. Write unit tests in `lib/db/schema.test.ts` asserting the shape of the schema definition — table names, presence of the unique constraints on `(etf_id, report_date)` and `(report_id, field_key)`, and the cascade behaviour declared on foreign keys. These tests must not require a live database connection.

## Acceptance criteria

- **AC1** — All seven tables are defined in `lib/db/schema.ts` with the exact column names and types from `data-model.md`.
- **AC2** — `UNIQUE (etf_id, report_date)` on `reports` and `UNIQUE (report_id, field_key)` on `report_values` both exist — these prevent duplicate ingestion.
- **AC3** — `pnpm db:generate` produces migration SQL, and the generated SQL is committed.
- **AC4** — The database client throws a clear, named error when `DATABASE_URL` is missing, rather than failing with an opaque connection error.
- **AC5** — `pnpm test` passes, including the new schema tests, without any database being reachable.
- **AC6** — `pnpm build` still succeeds.

## Out of scope

- No seed data (US-005).
- No queries beyond what the tests need — repositories and data-access functions come with the stories that use them.
- Do not run migrations against a real Neon database as part of this story; that happens in US-006, where the connection is verified end to end.

## Notes for verification

`report_date` is the date the report is *for*, not the date it was published — the two differ by roughly a day in this data source, and conflating them would misalign the entire history. Column comments should make this explicit.
