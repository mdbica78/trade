# US-018 — ETF detail page: historical values table
> Detailed by agent (story-planner), 2026-09-25 — PO to confirm at demo.

**Sprint:** 4 · **Epic:** EPIC-04 · **Depends on:** US-016
**Suggested model / thinking:** mid model, medium thinking. Complex (new dynamic route, history read model on PGlite, 10 ACs), so it is planned by `story-planner`.

## Context

FR8: "Clicking an ETF in the table opens a dedicated page with historical values for the monitored parameters of that ETF (table) [and] time-evolution charts …". The charts are US-019. This story builds the page and its history table.

FR4 stores "historically (with date), per ETF, per parameter". FR4.1 says a missing report leaves "that day … blank in the history (no value)". FR4.2 says a newly added ETF's history "starts empty".

US-016 provides the formatters (`formatNumber`, DEC-007; `formatReportDate`), the read pattern (`BatchRunner` + PGlite tests), and the "only `ok` rows are shown" rule (US-016 decision 2). On the home table the symbol already links to the newest PDF (FR7), so FR8's "clicking an ETF" needs a second click target (decision 1).

## Task

1. **Route** `app/etf/[symbol]/page.tsx`, an async Server Component rendered per request. Look the ETF up by exact `symbol`. An unknown symbol calls `notFound()` (404).
2. **Read model**, e.g. `lib/monitoring/history.ts`, same `db.execute(sql…)` + `BatchRunner` pattern as US-016:
   - `etf`: `symbol`, `name`, `isActive`;
   - `fields`: the ETF's tracked fields, ordered by `display_order`, then `field_key`, with `label_ro`/`label_en` from `field_catalog` for the ETF's `adapter_key` (`field_key` as the fallback label, as in US-016 decision 3);
   - `rows`: one per `ok` report of the ETF, newest `report_date` first, each with `reportDate` and, per tracked field, the stored `numeric_value` string or `null`.
   Keep this model independent of the table component: US-019 builds its chart series from it.
3. **Page content**: a heading with the symbol and the stored name, then the history table (a presentational component, e.g. `components/HistoryTable.tsx`, render-tested with props). Dates go through `formatReportDate`, values through `formatNumber`. An empty cell is empty.
4. **Home-table link** (decision 1): each home-table row gets a translated link (e.g. "Istoric" / "History") to `/etf/<symbol>` with `next/link`. The symbol keeps its PDF link from US-016.
5. **States**: no `ok` report yet → translated "no history yet" message. No tracked fields → translated message. Database error → translated generic message, never the exception text (as in US-016 AC9).
6. **Messages**: new keys in both catalogues.
7. **Tests**: PGlite tests for the read model; render tests of the table and the page states in `ro` and `en`; a test that the page calls `notFound()` for an unknown symbol, with the loader injected or mocked.

## Acceptance criteria

- **AC1** — Route. `/etf/<SYMBOL>` renders the page for that ETF: its symbol and stored name in the heading. The lookup is by exact symbol. An unknown symbol gives a 404 via `notFound()`. (FR8 "a dedicated page"; data model `etfs.symbol` UNIQUE)
- **AC2** — Navigation from the home table. Every home-table row has a translated link to `/etf/<symbol>` that is separate from the symbol's PDF link. The symbol's link from US-016 AC4 is unchanged. A render test checks both hrefs on the same row. (FR8 "Clicking an ETF in the table opens a dedicated page"; FR7 "symbol … linking directly to the most recent PDF report"; decision 1)
- **AC3** — History table.
  - One row per `ok` report of the ETF, newest `report_date` first.
  - One column per tracked field of the ETF, in `display_order` then `field_key` order, headed by the catalogue label for the locale.
  - Each cell is that report's stored value for the field, formatted with `formatNumber` (DEC-007). A field with no value in that report gives an empty cell.
  - A field the adapter stored but the ETF does not track never appears.

  (FR8 "historical values for the monitored parameters of that ETF"; FR4 "per ETF, per parameter"; FR2; DEC-007)
- **AC4** — Missing days are never filled. PGlite test: `ok` reports for 2026-09-21 and 2026-09-23 only → exactly two rows, 2026-09-23 then 2026-09-21. No row, value or carried-forward number exists for 2026-09-22. (FR4.1 "that day remains blank in the history (no value)"; AGENTS.md "Never guess a value"; decision 2)
- **AC5** — Only `ok` reports. A `parse_error` report, including one with stored values, adds no row. Its date does not appear in the table. (US-016 decision 2; FR4.1)
- **AC6** — States. An ETF with no `ok` report shows a translated "no history yet" message instead of an empty table. An ETF with no tracked fields shows a translated message. When the database read throws, the page shows a translated error message, does not throw, and contains neither the exception message nor any environment value. (FR4.2 "its history starts empty"; FR2; AGENTS.md secrets rule)
- **AC7** — Deactivated ETF. The page of an ETF with `is_active = false` still renders its stored history (decision 3). The home table does not list it (US-016 AC1). (Data model `etfs.is_active` "soft removal"; decision 3)
- **AC8** — Bilingual. Every user-facing string on the page and the new home-table link go through next-intl, with keys in both catalogues, and the key-parity test passes. Render tests in `ro` and `en` show the locale's headers, date format (US-016 decision 5) and decimal mark (DEC-007). The ETF's stored name is shown as stored, untranslated (US-004 out of scope: database content is not translated through next-intl). (FR8.1; DEC-007)
- **AC9** — Offline and build-safe. The read-model tests run on PGlite with the shipped statements. No test connects to Neon. `pnpm build` passes with `DATABASE_URL` unset. (AGENTS.md "Tests never call live Neon"; ADR-001)
- **AC10** — `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. (AGENTS.md Commands)

## Out of scope

- Charts (US-019).
- Deltas in the history table (FR8 asks for historical values; deltas are FR7, US-017).
- A PDF link per history row, pagination, date-range filters, CSV export.
- Blank rows for missing calendar days (decision 2, option B, only if the PO picks it).
- Editing tracked fields from this page (US-021, Sprint 5).
- Any database write or schema change.

## Decisions needed

1. **PRODUCT — how does "clicking an ETF in the table" open the detail page?** (non-blocking) FR7 makes the symbol a link to the newest PDF, and FR8 makes "clicking an ETF" open the detail page. One element cannot do both.
   - A: a separate, translated per-row link ("Istoric" / "History") to `/etf/<symbol>`. **This story implements it.**
   - B: add the ETF name as a column and link it to the detail page. The seeded names are long (e.g. "Fondul Deschis de Investiții BT Index România ETF BET-TR").
   - C: make the whole row clickable except the symbol. This nests interactive elements and is harder to use with a keyboard.
   - Recommendation: **A**.
2. **PRODUCT — missing days in the history table.** (non-blocking)
   - A: list only dates with an `ok` report. A missing day has no row, so it has no value (FR4.1). **This story implements it.**
   - B: list every calendar day between the first and the newest report, with blank rows for missing days. Under US-012 PRODUCT 2's literal reading, that adds two blank rows every week (Friday and Saturday).
   - Recommendation: **A**. The gaps are visible in the charts, which break the line on a missing day (US-019).
3. **PRODUCT — detail page of a deactivated ETF.** (non-blocking)
   - A: still reachable by URL and showing its stored history. Deactivation is a soft removal, and the data is kept. **This story implements it.**
   - B: 404 for an inactive ETF.
   - Recommendation: **A**. Nothing links to it from the home table, so it does not look monitored.

## Notes for verification

- The history query reads only `ok` reports and only the ETF's tracked `field_key`s. The reviewer checks both in the SQL, not only in the tests.
- Next.js 16 passes route `params` as a Promise to the page. The plan should follow the installed version's docs, and the `notFound()` test should use the same shape.
- `symbol` comes from the URL. It is only ever a bound parameter in the query, never interpolated into SQL text.
- The history grows by one row per ETF per stored day. Rendering all rows is fine for this sprint (data model notes: storage is trivial). Pagination is out of scope.
