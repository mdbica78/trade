## Task

1. **Schema (T-3).** In `lib/db/schema.ts`:
   - `home_display_settings`: `id` int PK CHECK `id = 1`; `show_absolute`, `show_percent`, `show_arrow` boolean NOT NULL default true.
   - `home_display_columns`: `field_key` text PK; `position` integer NOT NULL UNIQUE; nullable `show_absolute`, `show_percent`, `show_arrow` (null = follow the global switch).
   - `home_display_etfs`: `etf_id` int PK → `etfs.id` ON DELETE CASCADE; `visible` boolean NOT NULL.
   Then `pnpm db:generate` produces **one** migration (`drizzle/0002_*.sql` + snapshot + journal). It must be expand-only and pass US-048's guard. **Never run `db:migrate` or `drizzle-kit migrate`.** The production build applies it (DEC-023).
2. **Config module** `lib/config/home-display.ts` (DEC-016):
   - `getHomeDisplay`: the saved state, or "nothing saved" (sprint D-4: the single settings row exists or not).
   - `saveHomeDisplay`: validates, then replaces the rows of all three tables in **one batch**, and returns the saved state.
   - Validation rejects an unknown or inactive ETF id, a `field_key` not in `field_catalog`, and a duplicate position (and a duplicate `field_key`). Results use closed codes, the house pattern of `lib/config/*`.
   - Wiring through `lib/config/default-deps.ts`.
3. **Read model** (`lib/monitoring/home.ts`):
   - **Nothing saved** → exactly today's view model (P-1: all active ETFs, tracked union, all change parts on).
   - **Saved** → rows = active ETFs not hidden, in today's order. Columns = the saved `field_key`s by `position`, labelled from `field_catalog` (DEC-018 §3: labels identical across adapters). Each cell shows the ETF's newest-`ok` value for that key, or blank when that report has none, whether or not the ETF tracks it (FR7.3 "blank cell when an ETF has no such field").
   - Each column carries its effective `showAbsolute`/`showPercent`/`showArrow` (a per-column override wins, otherwise the global switch).
   - The loader also returns what the panel needs: every active ETF with its visible flag, every catalogue `field_key` with labels (and whether it is shown), and the three global switches.
   - If any of the three tables is missing (`42P01`), it falls back to the "nothing saved" view and logs one `[load-error]` line. It never fails the page.
4. **Home page UI** (spec rules 2 and 6; DEC-020 §6 title row and panel only):
   - A title row in `app/page.tsx`: translated title left, "Customize view" button right.
   - A client panel component, which the button toggles open above the table. It has three groups (ETFs, value columns, changes) of checkboxes, as in `mockup-home-dark-customize.png`. Panel list order and new-column position follow sprint D-4.
   - Each change calls **one server action**. The action sends the whole new state to `saveHomeDisplay`, revalidates `/`, and returns the saved state, which the panel then shows. There is no Save button.
   - Panel state logic lives in a pure module tested without a DOM.
   - **No** admin page and **no** admin-nav entry.
5. **Change-part switches in the table.** `components/HomeTable.tsx` renders the absolute and percent parts only when the column's effective switch is on. The arrow flag is carried in the view model now and rendered by US-036 (which adds the arrow). With every switch on (the default), `HomeTable`'s output is **byte-identical to today**, so existing `HomeTable` tests stay unchanged.
6. **Messages:** title, button, group headings, the three change labels, and the action's error text, in both catalogues.
7. **Docs.** `architecture/data-model.md`:
   - the three tables and their write rule (only `saveHomeDisplay` writes them, one batch, whole state);
   - the read side: optional tables with a 42P01 fallback;
   - replace the line "Migrations are generated locally … and applied to Neon only by the user" with the DEC-023 rule (the production build applies them; agents generate only; expand-only).

## Notes for verification

- **Why separate tables.** Drizzle selects every declared column, so new columns on `etfs`/`settings` would break the cron, admin and chat reads before the migration is applied (review T-3). The reviewer checks that no existing table gains a column.
- **Deploy window.** The code may go live a moment after the migration (DEC-023 §4) or, with `DATABASE_URL` unset in the build, before it. AC5's fallback is what makes both safe.
- **Two quick clicks.** Each click sends the whole new state, and the save replaces all rows in one batch, so the last write wins with no half state (review T-3). The panel shows the state the action returns.
- **Revalidation.** After a save, `/` is revalidated, so the table matches without a manual reload. A test asserts the action calls the revalidation.
- **Existing tests.** With default settings, `HomeTable` output must be byte-identical (Task 5), so any `HomeTable.test.tsx` change in this story is a red flag, unless it is a new test.
- **Manual QA (Codex):** capture `/` with the panel open at about 1200×560 in dark, and at 390 px. Compare with `mockup-home-dark-customize.png` and `mockup-home-phone.png` (AC10). Live, optional, user: sprint-09.md step 4.
