# US-030 — No-adapter degradation path, end to end
> Detailed by agent (story-planner), 2026-09-27 — PO to confirm at demo.

**Sprint:** 7 · **Epic:** EPIC-07 · **Depends on:** US-014, US-015, US-016, US-018, US-020, US-021, US-024, US-028
**Suggested model / thinking:** strong model, high thinking. Complex: a DB schema change with a migration, a change to the ingestion outcome path, and a change to the cron run budget (11 ACs). So it is planned by `story-planner`.

## Context

- **Section 3:** "If no adapter matches, the ETF is still shown in the list (**with a link to its report**), but automatic extraction is marked 'unavailable' — until a new adapter is added for that format."
- **Requirements §5 / FR13:** "the admin panel only flags that an adapter is missing". Operational visibility is "especially useful for ETFs without a matching adapter".
- **FR7:** the symbol is "clickable, linking directly to the most recent PDF report".
- **FR1, FR9:** any BVB ETF can be added, by chat or by form, and "both paths … operate on the same configuration model".
- **FR4.1, FR4.2:** no retries, no alerts, no backfill.
- **EPIC-07 "Done when":** "adding an arbitrary BVB ETF either works or degrades visibly and correctly."

What exists:
- **Ingestion** (`lib/ingestion/ingest-etf.ts`, US-014 AC1). A NULL or unregistered `adapter_key` returns `no_adapter` **before** discovery: "`fetch` is never called, nothing is written."
- **Home table** (`lib/monitoring/home.ts`, US-016 AC4/AC5). The symbol links to the `source_url` of the newest `reports` row that has one, and a no-adapter ETF has none. So today it shows the "extraction unavailable" marker **without** a link. That was out of scope for US-016, and the roadmap carry-forward assigns the link to this story.
- **Detection** (`lib/config/detect-adapter.ts`, US-020) already runs discovery at add and re-detect time. It discards the link it found.
- **Dashboard** (`/admin/operations`, US-024): the "adapter missing" flag, and translated outcome codes in the run log.
- **Chat** (US-028): `addEtf` through the same `lib/config/` layer. Its `addedNoAdapter` reply says "automatic extraction is unavailable" (sprint-06 forward note).
- **Detail page** (`/etf/<SYMBOL>`, US-018/US-019): for a no-adapter ETF, an empty history with no explanation.
- **Cron budget** (`app/api/cron/daily/route.test.ts` RT-7b): `seedEtfCount = 3` is hard-coded. US-013 plan R1: "a fourth active ETF breaks the 60 s worst case". A run the platform kills is swept to `failed` with no per-ETF lines (US-015).
- **PGlite helper** (`test/helpers/pglite.ts`): it applies only `drizzle/0000_init.sql`.

## Task

1. **Schema** (sprint decision 6). Add the table `etf_report_links`:
   - `etf_id` int PK, FK → `etfs.id` ON DELETE CASCADE;
   - `source_url` text NOT NULL;
   - `discovered_at` timestamptz NOT NULL.
   Add it to `lib/db/schema.ts`, and run `pnpm db:generate` locally to produce `drizzle/0001_*.sql`, which is additive. Change `test/helpers/pglite.ts` to apply every migration in journal order. Document the table and its write rule in `architecture/data-model.md`. **Never apply the migration to Neon** (the user does).
2. **Detection keeps the link** (sprint decision 5). `DetectionResult` carries the discovered report URL whenever discovery found one, whatever the adapter outcome. `addEtf` and `detectEtfAdapter` (`lib/config/etfs.ts`) upsert it into `etf_report_links`. No write happens when discovery found nothing.
3. **No-adapter branch of the daily run** (sprint decisions 5 and 7). For a NULL or unregistered `adapter_key`, `ingestEtf` makes exactly one discovery request and no download. If a link is found, it upserts `etf_report_links`. It writes no `reports` or `report_values` row. The outcome code stays `no_adapter`, and its `detail` says whether a link was found and stored.
4. **Link rule** (`lib/monitoring/home.ts`). The symbol links to the most recent known report link: the newest `reports.source_url` (US-016 AC4), or the `etf_report_links` row when that is newer or no report link exists. With no link at all, the symbol stays plain text (sprint decision 4 default).
5. **Detail page marker** (sprint decision 10). `/etf/<SYMBOL>` shows the translated "extraction unavailable" marker above the (empty) history when the ETF's adapter is not available. The flag comes from `lib/monitoring/history.ts`, with the same rule as US-016 AC5.
6. **Run deadline guard** (sprint decision 8). `runDailyIngestion` takes an injected clock and a deadline derived from `maxDuration`. Before starting each ETF, it checks that one ETF's worst case still fits: `MAX_REQUESTS_PER_ETF × CRON_FETCH_TIMEOUT_MS` plus a parse allowance and a finish reserve, all named constants. An ETF that does not fit is not started and gets the new outcome `not_attempted`. It is added to `INGEST_OUTCOME_CODES`, counts as an error, is written to `job_runs.log`, and is translated on `/admin/operations`. Replace RT-7b with a test over the same constants, with no hard-coded ETF count. `MAX_REQUESTS_PER_ETF` is shared with US-029 AC9: create it if US-029 has not, otherwise reuse it.
7. **Messages:** `not_attempted` and the detail-page marker, in both catalogues.
8. **Tests:** PGlite with every migration, for the form path and the chat path, recovery, and the guard with a fake clock. The plan lists every US-012/US-014 test it changes and the AC of this story that replaces it (sprint decision 7).

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1** — Schema and migration.
  - `etf_report_links` exists in `lib/db/schema.ts` with the columns, key and cascade of sprint decision 6.
  - `drizzle/0001_*.sql` is produced by `pnpm db:generate`. It is additive: it creates only this table and its constraint, and changes no existing table.
  - `test/helpers/pglite.ts` applies every migration listed in `drizzle/meta/_journal.json`, in order. A test proves the new table exists in a fresh PGlite database, and that deleting an ETF deletes its link row.
  - `architecture/data-model.md` documents the table and its write rule: one row per ETF, upserted, written only by adapter detection and the daily run's no-adapter branch, never read as a report.
  - No agent applies the migration to Neon (MANUAL-QA, sprint-07.md step 1).
  (Section 3 "with a link to its report"; sprint decision 6; data model "Write rules"; AGENTS.md "Migrations are generated locally, never applied to Neon by an agent")
- **AC2** — The form path stores the link (US-020 detection). PGlite tests mock detection's `fetch` over the BRD page fixtures and cover these cases:
  - `addEtf` of a new symbol whose discovery finds a report link upserts `etf_report_links` with that URL, whatever the detection reason that follows (`detected`, `no_match`, `ambiguous`, `unreadable`, or a download `fetch_error`). The stored `adapter_key` and the returned reason are exactly as today.
  - A symbol whose discovery returns `not_found` or `error` gets no link row.
  - No case writes a `reports`, `report_values` or `tracked_fields` row (FR4.2).
  - `detectEtfAdapter` (re-detect) updates the link row the same way. When discovery finds nothing, it keeps the existing row.
  - The `/admin/etfs` list and the dashboard's "adapter missing" flag (US-024) show the ETF as before.
  (Section 3; FR7 "the most recent PDF report"; FR9; FR4.2; sprint decision 5; US-020 AC3, AC7)
- **AC3** — The daily run's no-adapter branch. For an ETF with `adapter_key` NULL, and for one with an unregistered key, `ingestEtf` does the following:
  - it makes exactly one discovery request and no download (`fetch` spy);
  - it writes no `reports` or `report_values` row;
  - on `found`, it upserts `etf_report_links` with that URL and a `discovered_at` from the run's clock;
  - on `not_found` or `error`, it leaves an existing link row unchanged;
  - it returns `no_adapter` in every case, with a `detail` that says whether a link was stored, and never throws;
  - an ETF processed after it is unaffected.
  US-014 AC1's "`fetch` never called" expectation is replaced by this AC, as a specified behaviour change. The plan lists each changed test.
  (Section 3; FR4.1 "no automatic retries"; FR13; sprint decisions 5 and 7; US-014 AC1)
- **AC4** — Visible everywhere, with the link.
  - **Home table.** A no-adapter ETF with a stored link shows its symbol as a link to that URL, opening in a new tab, next to the "extraction unavailable" marker. With no link at all, the symbol is plain text (sprint decision 4 default, US-016 AC4). PGlite tests of the shipped loader cover three cases: link only; a report newer than the link (report wins); a link newer than the last report (link wins).
  - **Detail page.** `/etf/<SYMBOL>` of a no-adapter ETF shows the translated marker above its empty history, and an ETF with an adapter does not (sprint decision 10).
  - **Dashboard.** `/admin/operations` shows the "adapter missing" flag and the translated `no_adapter` log line for it.
  - Every value, date and timestamp on these pages goes through the existing formatters (`formatNumber`, `formatReportDate`, `formatDateTime`). No URL is ever built from the symbol, the `bvb_url` or a date.
  (Section 3 "still shown in the list (with a link to its report) … marked 'unavailable'"; FR7; FR13; requirements §5; sprint decisions 4, 5 and 10; DEC-007; P5)
- **AC5** — The same end state via the chat. In a PGlite test with the fake provider (US-028 pattern), "add ETF XYZ" for a symbol whose detection finds a link but no adapter does the following:
  - it gives the chat's `addedNoAdapter` reply, in `ro` and `en`;
  - it leaves the same `etfs` row, the same `etf_report_links` row and the same home-table row as adding XYZ through the form.
  A test compares the two paths' resulting rows directly (all columns except generated ids and the `created_at` / `discovered_at` timestamps).
  (FR1, FR9 "both paths (chat and form) operate on the same configuration model"; FR8.1; DEC-016; sprint-06 forward note)
- **AC6** — Recovery once an adapter exists. After a no-adapter ETF is given a registered adapter (`setEtfAdapter` or a re-detect that returns `detected`), the next `ingestEtf` does the following:
  - it takes the normal path (discovery + download) and stores an `ok` report under the write rules (DEC-010);
  - the home row then shows no marker, shows its values, and links to that report's `source_url`;
  - days before recovery stay blank, with no backfill.
  (Section 3 "until a new adapter is added for that format"; FR4.1, FR4.2; FR7; DEC-010)
- **AC7** — Run deadline guard. With a fake clock and a fake `ingest`:
  - an ETF whose worst case no longer fits before the deadline is not started, and gets `not_attempted` with a one-line detail;
  - every ETF before it keeps its real outcome;
  - `summarizeRun` counts `not_attempted` as an error;
  - the run finishes normally, and `job_runs` gets a final status (`partial` when some ETF succeeded) and one log line per ETF.
  `not_attempted` is in `INGEST_OUTCOME_CODES`. The US-024 test that iterates the codes finds its message key in both catalogues.
  RT-7b is replaced by a test over the same named constants, with no hard-coded ETF count. It asserts that one ETF's worst case, the parse allowance and the finish reserve fit inside `maxDuration` (still 60). `STALE_RUN_THRESHOLD_MS` (RT-15) is unchanged.
  (FR13 "history of cron runs (success/failure)"; EPIC-03 "failures are visible rather than silent"; section 4 Vercel Hobby; sprint decision 8; US-013 plan R1; US-015)
- **AC8** — Failure handling and link safety.

  - A link write that fails during `addEtf` does not undo the `etfs` insert. The result is reported as today.
  - Only URLs that discovery accepted (absolute `http`/`https` ending in `.pdf`, US-007) are stored. A test with a `javascript:` href in the page fixture stores nothing.
  - Pages render the link as an attribute only. A read failure keeps each page's existing translated error state, with no exception text (US-016 AC9 pattern).

  (FR8.1; AGENTS.md "Every UI string goes through next-intl")

  - No test connects to Neon or bvb.ro. Detection and discovery use the committed page fixtures through a mocked `fetch`.

## Out of scope

- A symbol link to the bvb.ro instrument page when no PDF URL is known (sprint decision 4 recommendation; it ships only if the PO chooses it).
- Keeping a working adapter through a transient re-detect failure (Sprint 5 audit N3, sprint decision 9). Nothing changes unless the PO answers. If they do before this story starts, the change is confined to `detectEtfAdapter` in `lib/config/etfs.ts`.
- Raising `maxDuration` above 60. That needs a live Fluid-compute check by the user (sprint decision 8).
- Retrying or re-running a `not_attempted` ETF (FR4.1 "no automatic retries").
- Alerts (requirements §6), and editing adapters from the admin area (requirements §5).
- A `reports` row for a no-adapter ETF (sprint decision 6: it would need a guessed `report_date`).

The RT-7b successor asserts `MAX_REQUESTS_PER_ETF × CRON_FETCH_TIMEOUT_MS + PARSE_ALLOWANCE_MS + FINISH_RESERVE_MS ≤ CRON_MAX_DURATION_S × 1000`, and a second assertion shows it would fail if `MAX_REQUESTS_PER_ETF` were raised past the budget (computed, not hard-coded). RT-7a and RT-15 stay unedited.
2. **Deadline wiring.** `runDailyJob` (`lib/cron/daily-job.ts:27`) already takes `startedAt = deps.now()` before the stale sweep. Pass that instant (or the deadline derived from it) through `runIngestion` into `runDailyIngestion`, together with the same `now`. No test sleeps; the guard test advances a fake clock inside the fake `ingest`.
3. **`not_attempted` needs no special case in `summarizeRun`**: `isErrorOutcome` classifies by exclusion (`lib/ingestion/job-run-summary.ts:13-15`). Add it to `INGEST_OUTCOME_CODES` and the `IngestOutcome` union; `lib/admin/operations-messages.test.ts` then forces both catalogue keys. Also update JS-3a and IF-8a/b if they enumerate codes.
4. **Ingest deps.** The no-adapter branch needs a link writer and a clock in `IngestDeps`. 5. **Detection result.** Add an optional report URL to `DetectionResult`; `DetectionReason` and every reply mapping (admin `result-messages`, chat `reply-messages`) stay byte-identical. 6. **Link-rule comparison.** Name it in the plan and pin it in AC4's three PGlite cases: the newest `reports` row with a `source_url` (today's order: `report_date desc, id desc`) against `etf_report_links.discovered_at`, comparing its `fetched_at`; a NULL `fetched_at` counts as older than any link row.
7. **Deploy order.** The daily run and add/re-detect already survive a missing `etf_report_links` table through AC8. The home loader will show its error state until the user migrates Neon; the QA checklist says so first (sprint step 1). Do not add a "table missing" fallback in the loader.
