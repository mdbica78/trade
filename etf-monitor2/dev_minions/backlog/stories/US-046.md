# US-046 — Spike: user-defined raw field from a report label (decide, do not build)
> Detailed by agent (story-planner), 2026-10-02 — PO to confirm at demo.

**Sprint:** 11 · **Epic:** EPIC-08 · **Depends on:** None; independent investigation
**Suggested model / thinking:** mid model, high thinking. Bounded research/spike; no implementation.

## Context

FR19 identifies user-requested raw fields read from report labels as a separate, proposed spike;
it does not decide whether to support them or define eligible labels, report formats or persistence.
The approved Sprint 11 review explicitly says US-046 is not an implementation story. DEC-022 §9
keeps raw-field support outside US-043–045, whose widget definitions accept only existing numeric
adapter-catalogue keys. The binding technical constraint for any future support is deterministic,
adapter-specific label parsing; an AI model must never extract values or author or execute parser
code.

## Task

Investigate the feasibility, bounded options, trade-offs and safety/maintenance implications of
possible user-defined raw fields using existing architecture and committed fixtures only. Record
findings and a recommendation in `dev_minions/verification/US-046-spike.md`; leave the product
outcome **PROPOSED — NEEDS USER**. Make no source, test, schema, prompt, catalogue, adapter,
fixture or extraction change. This spike must not delay or alter US-043–045.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1 — Bounded feasibility investigation.** The spike examines the current adapter/catalogue
  model and existing report-label parsing boundary, using repository sources and already committed
  fixtures only; `verification/US-046-spike.md` records what would need to change for a requested
  raw field and distinguishes known facts from assumptions. No live BVB/network fetch is part of
  the investigation.
  (FR19; Sprint 11 review, “US-046 is not an implementation story”)
- **AC2 — Options and trade-offs.** `verification/US-046-spike.md` compares at least: (a) keep raw-field
  requests unsupported/catalogue-only, and (b) if support is considered, require explicitly mapped
  labels scoped to an adapter/report format. It discusses deterministic parsing, ambiguity,
  validation/catalogue persistence, historical availability, and maintenance without claiming
  unsupported labels can be safely inferred. (FR19; DEC-022 §9; Sprint 11 review, “Extraction
  boundary”)
- **AC3 — Recommendation remains non-binding.** The record in `verification/US-046-spike.md` gives
  a recommendation for the PO to
  consider—prefer explicit adapter/report-format label mappings if support is pursued—and clearly
  labels the product outcome **PROPOSED — NEEDS USER**. It does not present that recommendation as
  a decision, alter DEC-022, or create a dependency or user-step blocker for US-043–045.
  (FR19; Sprint 11 review, “US-046 unresolved product question”)
- **AC4 — No implementation or extraction expansion.** The spike changes no application code,
  tests, database/schema/migration, prompt, adapter, catalogue, PDF fixture or extraction behavior;
  it does not produce model-written parser code or parse arbitrary labels. Review the spike's
  scoped file changes to verify the result is documentation-only and confined to its verification
  record. (FR19; DEC-022 §9; Sprint 11 review, “US-046 is not an implementation story”)

## Out of scope

Any decision to support raw fields; raw-field UI/chat actions; catalogue or schema changes; parser,
adapter, prompt or extraction changes; arbitrary model-interpreted labels; fixture downloads;
backfill; changes to the closed numeric-catalogue widget field contract.

## Notes for verification

The deliverable is a bounded findings/options/recommendation record, not code or a test suite.
The spike should not use live network or secret-bearing inputs. Its recommendation is for the PO;
only a later accepted product decision and separately authorized story can change extraction scope.
