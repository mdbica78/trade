# US-019 — ETF detail page: time-series charts for tracked fields
> Detailed by agent (story-planner), 2026-09-25 — PO to confirm at demo.

**Sprint:** 4 · **Epic:** EPIC-04 · **Depends on:** US-018
**Suggested model / thinking:** mid model, medium thinking. Complex (first client-side chart component, a new runtime dependency already chosen by ADR-001, 8 ACs), so it is planned by `story-planner`.

## Context

FR8: the detail page shows "time-evolution charts, styled similarly to the charts on bvb.ro, but limited strictly to the user's parameters of interest (not everything the BVB site offers)". ADR-001 chose **Recharts** for charts ("React-native API, good enough for time series"). It is not installed yet (`package.json`).

US-018 provides the page, the history read model (one entry per `ok` report date, values per tracked field, as stored strings) and the empty states. US-016 provides `formatNumber` (DEC-007) and `formatReportDate`, written as pure functions so a client component can use them.

FR4.1 says a missing report leaves "that day … blank in the history (no value)". On a chart, that means a gap, not a line drawn through the missing day.

## Task

1. **Dependency**: add `recharts` to `dependencies` at an exact version that supports the installed React 19 (ADR-001). No other new runtime dependency.
2. **Series builder**, pure, e.g. `lib/monitoring/chart-series.ts`: from US-018's history model and one `field_key`, build the points in ascending date order. There is one point per calendar day from the oldest to the newest `ok` report date: `{ date, value: number | null, display: string | null }`. `value` is only the plotting position. `display` is the stored string, which is what the user reads. A day without an `ok` report, or without a value for the field, has `value: null` and `display: null`.
3. **Chart component**, a client component (`"use client"`, e.g. `components/FieldChart.tsx`). It receives the points and the already-translated labels as props, and renders one line chart with `connectNulls={false}`. The tooltip shows `formatReportDate(date)` and `formatNumber(display)`. The Y-axis ticks use the same no-grouping, locale-decimal rule (DEC-007). The X-axis ticks use `formatReportDate`.
4. **Page**: below US-018's history table, one chart per tracked field in the table's column order (`display_order`, then `field_key`), each titled with the field's catalogue label for the locale. The server page passes only plain data to the client component. The database is never read from the client.
5. **States**: with no `ok` report, no chart is rendered (US-018's "no history yet" message covers it). A tracked field with no value on any date shows a translated "no data for this field" message in place of its chart.
6. **Messages**: new keys in both catalogues.
7. **Tests**:
   - pure tests for the series builder and for the tooltip and tick formatting functions;
   - a render test of the page in `ro` and `en` that asserts one chart section (heading plus container) per tracked field.

   Recharts may render no SVG during server rendering, so assert the section and the props passed to the chart, not SVG internals.

## Acceptance criteria

- **AC1** — One chart per tracked field. The detail page has exactly one chart per tracked field of the ETF, in `display_order` then `field_key` order, titled with the catalogue label for the locale. A field the ETF does not track has no chart, even when values for it are stored. (FR8 "limited strictly to the user's parameters of interest"; FR2; decision 1)
- **AC2** — Series and gaps. Series-builder tests:
  - points are in ascending date order, one per calendar day from the oldest to the newest `ok` report date;
  - with `ok` reports on 2026-09-21 and 2026-09-23 only, there are three points and 2026-09-22 has `value: null` and `display: null`;
  - a `parse_error` report contributes no value. The builder only receives US-018's history model, which holds `ok` rows only (US-018 AC5). So this is proven by a test that feeds the builder from the read model over a PGlite database that contains a `parse_error` report with a stored value, not by a pure test;
  - no value is ever interpolated or carried forward.

  The chart component sets `connectNulls={false}`, so the line breaks at a missing day. Every point with a value is drawn as a dot (the line's `dot` is not `false`). Without dots, a single stored day, which is the normal state of a newly added ETF (FR4.2), or an isolated day between two gaps would draw nothing. A test checks the props passed to the line. (FR4.1 "that day remains blank in the history (no value)"; AGENTS.md "Never guess a value"; US-016 decision 2; decision 2)
- **AC3** — Values read exactly. The tooltip text for a point is the formatted date plus `formatNumber` of the stored string. For example, VUAN stored as `54.1373` reads `54,1373` in `ro` and `54.1373` in `en`, never a float re-rendering. Y-axis tick labels contain no grouping character in either locale. The tooltip and tick functions are pure and unit-tested. (DEC-007; FR8.1; US-016 decision 5)
- **AC4** — Empty states. With no `ok` report, no chart is rendered. A tracked field without a value on any date shows a translated "no data for this field" message instead of an empty chart. (FR4.2 "its history starts empty"; FR8)
- **AC5** — Bilingual. Every user-facing string (section headings, empty messages, tooltip and axis labels) goes through next-intl, with keys in both catalogues, and the key-parity test passes. Render tests in `ro` and `en` show the locale's field labels. (FR8.1; AGENTS.md "Every UI string goes through next-intl")
- **AC6** — Dependency. `recharts` is in `dependencies` at an exact version. It is the only new direct runtime dependency. The one exception is a peer dependency that `recharts` itself declares and pnpm does not install on its own (for example `react-is`, at a version that matches React 19). The plan names it. A clean `pnpm install --frozen-lockfile` from an empty `node_modules` exits 0, and `pnpm-workspace.yaml` contains no unresolved build-approval entry (the US-008 round 1 finding). (ADR-001 "Charts: Recharts"; AGENTS.md "New runtime dependency")
- **AC7** — Server/client boundary. The chart is a client component that receives only plain serialisable props (points, labels, locale). No database module is imported into a client component. `pnpm build` passes with `DATABASE_URL` unset. (ADR-001; AGENTS.md "Secrets only in environment variables, server-side")
- **AC8** — `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. (AGENTS.md Commands)

## Out of scope

- A date-range selector, zoom, or comparison between ETFs (decision 2).
- Deltas or percentage changes on the chart (FR7 is the home table).
- Charts of untracked fields, or of anything else the BVB site offers (FR8 "not everything the BVB site offers").
- Any database write or schema change.

## Decisions needed

1. **TECHNICAL — one chart per field, or one combined chart?**
   - A: one chart per tracked field. The seeded fields mix units (`RON` vs `count`, `field_catalog.unit`) and magnitudes (net asset around 4×10⁸ vs VUAN around 11), so one shared Y-axis would flatten every series but one.
   - B: one chart with several lines and two Y-axes. This is limited to two units and hard to read.
   - Recommendation: **A**. For the in-loop `tech-lead` to settle.
   - **Decided: A** (tech-lead sprint review, 2026-09-25). In the seed, `field_catalog.unit` mixes `RON` and `count`, and magnitudes run from about 10¹ to 10⁸. A shared axis would make every series but one unreadable. FR8 says "charts", plural.
2. **PRODUCT — gaps and time range.** (non-blocking) bvb.ro's instrument charts offer range buttons. FR8 asks for a similar *style*, limited to the user's parameters.
   - A: break the line at every missing calendar day (literal FR4.1 "blank"), and show the whole stored history with no range selector. **This story implements it.** Under US-012 PRODUCT 2's literal reading, the line breaks every week around Friday and Saturday.
   - B: connect the stored points across missing days. This looks smoother but hides the missing days.
   - C: A plus a range selector (1M / 3M / 1Y / all), as a follow-up story.
   - Recommendation: **A** now, and C as a follow-up if the PO wants it.

## Notes for verification

- `value: number` is the only place in Sprint 4 where a stored decimal becomes a float, and only to position the point. Every text the user reads comes from `display`. The reviewer checks that the tooltip formats `display`, not `value`.
- `recharts` and its dependencies must not require approving install scripts. If `pnpm add` prompts for one, resolve it explicitly in `pnpm-workspace.yaml` (`false` unless the build needs it) and run the clean-install proof (AC6), as US-008 learned the hard way.
- `pnpm-workspace.yaml` has a `minimumReleaseAgeExclude` list, which means a minimum package release age is in force here. If the newest `recharts` is too recent, pin the newest version old enough to pass. Do not add an exclude entry unless the plan justifies it. (Tech-lead sprint review, 2026-09-25.)
- If `ResponsiveContainer` renders nothing without a measured parent (server render, tests), give the chart container an explicit height in CSS. Do not skip the component in tests.
- Whether the charts are "styled similarly to the charts on bvb.ro" is a PO judgment, not an automated criterion.
- **Manual QA (live, user):** sprint-04.md steps 6 and 7. Compare with the chart on the instrument's bvb.ro page, then hover a point and check the date and value against the history table.
