# US-013 — Daily cron endpoint and Vercel Cron configuration
> Detailed by agent (story-planner), 2026-09-24 — PO to confirm at demo.

**Sprint:** 3 · **Epic:** EPIC-03 · **Depends on:** US-012
**Suggested model / thinking:** mid model, medium thinking. Complex (cron/infra, route auth, 10 ACs), so it is planned by `story-planner`.

## Context

FR3 asks for a daily download of the latest report for every monitored ETF. The requirements pick Vercel Cron on the Hobby plan, which allows one cron job per day (section 4; FR12 note). ADR-001 fixes the shape: "The cron endpoint is a protected API route (`/api/cron/daily`) invoked by Vercel Cron once per day", in the same Next.js project as the UI.

US-006 already documented `CRON_SECRET` in `README.md` as "shared secret the daily cron route checks on the `Authorization` header … Reserved for Sprint 3", and asked the user to set it in Vercel. When that variable is set, Vercel Cron sends `Authorization: Bearer <CRON_SECRET>` with its request (Vercel docs, "Securing cron jobs". Verify at implementation time).

US-012 provides `ingestEtf` for one ETF. This story loads the active ETFs, runs `ingestEtf` for each, protects the route, and registers the schedule. The `job_runs` row is added by US-015.

## Task

1. **Daily runner**, e.g. `lib/ingestion/run-daily.ts`: `runDailyIngestion(deps)`.
   - Load every ETF with `is_active = true`, with its `tracked_fields` (field keys, ordered by `display_order`, then `field_key` for a deterministic tie-break). Inactive ETFs are not processed (FR1 "stop tracking"; data model `etfs.is_active` "soft removal from monitoring"). The Drizzle loader filters on `is_active = true`, and the runner also skips any inactive ETF a loader returns, so AC2's fake-loader test proves real behaviour.
   - Call `ingestEtf` once per active ETF, sequentially. This keeps the load on bvb.ro small and the logs deterministic. The plan may justify limited concurrency if the duration budget (Notes) needs it.
   - One ETF's failure, or an exception thrown for it, never stops the others. Each ETF's outcome is collected. An exception thrown by `ingestEtf` (which should never happen, US-012 AC6) is recorded as outcome code `internal_error` with the error message as detail, so it is never lost and US-015 counts it as an error.
   - Return `{ etfs: [{ symbol, outcome }] }`. US-015 extends this.
2. **Route**, `app/api/cron/daily/route.ts`, `GET` only. Keep the logic in a testable handler, e.g. `handleDailyCron(request, deps)`, and leave the route file thin.
   - Read `CRON_SECRET` from the environment at request time.
   - If it is unset or empty → `500` with a generic "cron not configured" message. Nothing runs (fail closed).
   - If `Authorization` is not exactly `Bearer <CRON_SECRET>` → `401`. No database access, no ingestion.
   - Otherwise run `runDailyIngestion` and return `200` with a JSON summary: per ETF, the symbol and the outcome code and detail from US-012/US-014.
   - A failure before any ETF is processed (e.g. `MissingDatabaseUrlError`, or the ETF query fails) → `500` with a short message.
   - Responses never contain `CRON_SECRET`, `DATABASE_URL` or other environment values.
   - Route segment config: `runtime = "nodejs"`, `dynamic = "force-dynamic"` (never cached or prerendered), and an explicit `maxDuration` within the Hobby plan limit (Notes).
3. **`vercel.json`** at the repo root, with exactly one cron entry: `{ "path": "/api/cron/daily", "schedule": "<M> <H> * * *" }`. The schedule is TECHNICAL decision 1 below.
4. **Build.** This is the first time `unpdf` is bundled into a Next.js server route (Sprint 2 forward note). If `pnpm build` or the route fails because of it, add `serverExternalPackages: ["unpdf"]` in `next.config.ts` first. pdf.js may also try to resolve the optional `canvas` package, which is installed with its build disabled (`pnpm-workspace.yaml` `allowBuilds.canvas: false`, US-008). Record in the plan what was needed.
5. **README.** Replace "Reserved for Sprint 3" for `CRON_SECRET`. Document the schedule and its source (`vercel.json`), how to trigger a run by hand (curl with the bearer header, locally and on the deployment), that Vercel runs cron only on Production deployments, and that until US-023 the hour is changed by editing `vercel.json` and redeploying.
6. **Tests.** Build `Request` objects directly against the handler. Use a fake runner/`ingestEtf` and a fake ETF loader. Read `vercel.json` from disk in a test.

## Acceptance criteria

- **AC1** — Auth. With `CRON_SECRET` set:
  - no `Authorization` header, a wrong scheme, or a wrong secret → `401`, and neither the ETF loader nor `ingestEtf` is called;
  - the correct bearer → the run happens;
  - `CRON_SECRET` unset or empty → a non-2xx response and nothing runs, even with an `Authorization: Bearer ` header.

  (ADR-001 "protected API route"; README `CRON_SECRET` contract from US-006; AGENTS.md "Secrets only in environment variables, server-side")
- **AC2** — Every active ETF is processed exactly once, and inactive ETFs are not processed. Each ETF receives its tracked field keys in `display_order`. Tested with a fake loader that returns active and inactive ETFs. (FR1; FR3; FR9 `is_active`; FR2)
- **AC3** — Isolation. When one ETF's `ingestEtf` returns a failure or throws, the remaining ETFs are still processed, and the summary contains an outcome for every active ETF; a throw appears as `internal_error` with its message. (FR13 "failures visible"; EPIC-03 "failures are visible rather than silent")
- **AC4** — No retries: one `ingestEtf` call per active ETF per request, whatever the outcome. (FR4.1)
- **AC5** — `vercel.json` has exactly one cron entry, with `path` `/api/cron/daily` and a once-a-day schedule: minute and hour are single numbers, and day-of-month, month and day-of-week are `*`. A test parses the file and asserts this. (Section 4 "once per day"; FR12 note "a single cron job per day"; ADR-001)
- **AC6** — Responses:
  - a completed run → `200` with a JSON body listing every processed ETF's symbol and outcome, even when some ETFs failed;
  - a run that cannot start (missing `DATABASE_URL`, ETF query rejected) → `500` with a short message;
  - no response body contains the secret or the database URL. A test asserts that the secret value does not appear.

  (FR13; AGENTS.md secrets rule)
- **AC7** — The route exports only `GET`, with `runtime = "nodejs"`, `dynamic = "force-dynamic"` and an explicit `maxDuration`. `pnpm build` succeeds with the route importing the real ingestion chain, including `unpdf`. The plan records any `next.config.ts` change. (ADR-001; Sprint 2 forward note on `serverExternalPackages`)
- **AC8** — `README.md` documents: `CRON_SECRET` as in use, the schedule and where it is set, the manual trigger command, Production-only cron execution, and how to change the hour until US-023. (US-006 AC5 convention; FR12)
- **AC9** — **MANUAL-QA** (sprint-03.md steps 1–4, 6). On the deployment:
  - Vercel's Cron Jobs settings list exactly one job for `/api/cron/daily`;
  - an unauthenticated request returns `401`;
  - a request with the right bearer returns `200` with one outcome per seeded ETF, and Neon shows the new `reports`/`report_values` rows;
  - on a following day, a run happens without manual action.

  (FR3; EPIC-03 "Done when")
- **AC10** — `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. (AGENTS.md Commands)

## Out of scope

- `job_runs` bookkeeping (US-015). This story's summary is only the response body.
- Reading the hour from `settings.cron_hour_utc`, or changing the schedule from the UI (US-023, FR12).
- Authentication for users or the admin area (requirements section 6, roadmap).
- Retrying failed ETFs, alerts, notifications (FR4.1; section 6).
- A local CLI runner. The manual trigger is the route itself, via `pnpm dev` + curl.

## Decisions needed

1. **TECHNICAL — initial cron schedule (UTC).** The requirements leave the hour to the user (FR12, US-023) and give no default. Evidence: BVB filed the depositary reports at 09:09–09:34 Bucharest time on the capture days (`test/fixtures/bvb/README.md` §2, §7), which is 06:09–06:34 UTC in summer (EEST) and 07:09–07:34 UTC in winter (EET). Vercel's Hobby cron may fire anywhere within the scheduled hour (verify in Vercel docs at implementation time).
   - A: `0 8 * * *`. Earliest safe hour in winter, with 25 min of margin at worst.
   - B: `0 10 * * *`. At least 2.5 h of margin after the observed filings in either season, and still the same Bucharest working day.
   - Recommendation: **B**. A report filed after the run is not retried (FR4.1). The next day's run takes the next report, so a late filing leaves that day blank. More margin means fewer blanks, and an earlier run gains nothing because the report is for the previous day anyway. For the in-loop `tech-lead` to settle. The PO can change it at the demo, and FR12/US-023 make it the user's setting later.
   - **Decided: B, `0 10 * * *`** — tech-lead sprint review 2026-09-24 (`verification/SPRINT-03-review.md`). Valid on Hobby (one run per day; Vercel may fire anywhere inside 10:00–10:59 UTC), ≥ 2.5 h after the latest observed filing in either season, reversible by editing `vercel.json`.

## Notes for verification

- **Duration budget.** Sequential worst case ≈ number of ETFs × (discovery timeout 15 s + PDF timeout 15 s + parse), about 90 s+ for the three seeded ETFs if bvb.ro hangs. The plan must check Vercel's current Hobby function duration limit (it depends on whether Fluid compute is enabled) and set `maxDuration` accordingly. If the limit is lower than the worst case, reduce the per-request timeouts through the existing `timeoutMs` injection rather than adding concurrency.
- **Constant-time comparison** of the bearer value (e.g. `crypto.timingSafeEqual` on equal-length buffers) is good practice. It is not an AC.
- Vercel Cron issues a `GET`. There is no need for `POST`.
- `getDb()` throws `MissingDatabaseUrlError` lazily. Make sure it is caught inside the handler and mapped to `500` (AC6), not left to become an unhandled error.
- The JSON summary is not UI, so no next-intl is needed. Keep outcome codes stable because US-015 and US-024 reuse them.
- Sprint 2 audit N1: if this story touches `package.json`, pin `"unpdf": "0.11.0"` exactly.
- Agents never create or change Vercel settings, and never set env vars (AGENTS.md). Those steps are AC9 / the QA file.
