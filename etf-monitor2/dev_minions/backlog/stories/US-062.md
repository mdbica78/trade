# US-062 — Daily job hour editable in the app

Sprint 14. Depends on: DEC-030 (Decided by the Technical Lead in `decisions/DEC-030-user-editable-cron-hour.md`). The user's five Sprint 14 needs are the business requirements; this is BR4.

## Acceptance criteria
- **AC1 (FR12, FR13; Sprint 14 BR4):** After bearer authentication, the daily endpoint runs only when UTC hour is at or after the configured hour and a same-day run has not been claimed. Earlier pings and duplicate/already-run pings return HTTP 200 with a closed `skipped` reason and create no `job_runs` row. A single atomic claim prevents concurrent hourly pings from starting two runs.
- **AC2 (FR12):** `cron_hour_utc` remains nullable for legacy rows; `NULL` means hour 10 UTC. The admin form requires an integer 0–23, cannot clear the setting, and shows the corresponding Europe/Bucharest time. The setting is hour-only.
- **AC3 (FR12, FR13):** `/admin/cron` explains that an hourly external ping is required, displays the saved effective hour and the latest run, and no longer instructs the user to edit `vercel.json`.
- **AC4 (FR12, FR13):** Ship an hourly GitHub Actions workflow calling `/api/cron/daily` with bearer `CRON_SECRET`, plus README setup steps naming required repository secrets without values. Keep the existing daily Vercel cron entry as a safety net; both callers use the same gate.
- **AC5 (FR12, FR13):** Tests cover UTC date boundaries, before/at/after-hour behavior, catch-up, all prior statuses counting as a run, empty/invalid stored setting fallback, skipped no-write behavior, concurrent claim collision, unauthorized request no DB access, and route result shape. Replace BC-8 deliberately to assert that only the gated cron path reads the setting.
- **AC6 (FR8.1, FR12, FR13):** All visible strings are localized in Romanian and English; migrations are expand-only and generated offline; typecheck, lint, full suite and offline build pass.

## Data / schema impact
**Migration required.** Add nullable `job_runs.scheduled_date_utc date` and a unique index on it (historical rows remain `NULL`), plus a btree index on `job_runs.started_at` for the UTC-day range check. Generate the expand-only migration with `pnpm db:generate`; never run a production migration. Update Drizzle schema, snapshots/journal, data-model documentation and PGlite migration tests. No settings migration: `cron_hour_utc` already exists.

## Schedule semantics (binding)
- Hour gate is `now.getUTCHours() >= effectiveHour`; missing/NULL setting resolves to 10. Admin saves only 0–23; no minute or timezone setting.
- UTC date is the invocation's date. Any `job_runs` row whose `started_at` falls in `[UTC midnight, next UTC midnight)` counts regardless of `running`, `success`, `partial`, or `failed`. Once a run starts, the day is consumed; no same-day retry after failure.
- The route first checks the gate and then atomically inserts a `running` claim row keyed by `scheduled_date_utc`, only if no same-UTC-day `started_at` row exists. Unique conflict or prior row means `already_ran`. The claim row is the eventual run row and is finalized by the normal job-run lifecycle.
- Unauthorized and pre-hour requests do not read/change `job_runs`; skipped responses never write a row. Authorization remains bearer `CRON_SECRET` and is checked before schedule/database work.
- `/admin/cron` displays Bucharest time but stores and gates UTC. The Vercel cron remains unchanged; if it arrives after the configured hour it can catch up, and the unique daily claim prevents a duplicate.

## Scope
No retry policy, minute selection, weekday scheduling, Vercel settings changes, or live credential setup. Repository secrets are a later user-only step.
