# US-057 — Custom OpenAI-compatible provider with a URL-bound key

## Context
The user's chat transcript of 2026-10-05 shows the chat failing on plain requests. Causes and design: the binding DEC above, section "How the chat works today". No user step: any migration rides the deploy (DEC-023).

## Task
1. Table `ai_custom_providers` (id, name, base_url, created_at) — expand-only migration via `pnpm db:generate` (the deploy applies it; never run it against Neon). Missing table = no custom providers (42P01 fallback).
2. Admin form on `/admin/ai`: add / edit / delete a custom provider (name, https base URL). Validation: https only, no credentials/query/fragment, no IP literal, no localhost/private hosts, ≤ 200 chars; max 5.
3. The stored key's encryption AAD includes the base URL; changing or deleting the URL deletes that provider's stored key in the same batch.
4. Custom providers appear in the provider selector and in the chat's provider resolution; requests go to `<base_url>/chat/completions` through the existing OpenAI-compatible adapter.

## Acceptance criteria (confirmed by the PO, 2026-10-05)
- AC1 — Gates: typecheck, lint, build, full test suite and `scripts/claude/predeploy-check.sh` pass; no existing behaviour test is loosened (AGENTS.md); deliberate test changes are listed in HANDOVER with the reason.
- AC2 — URL validation table (accepts a normal https URL; rejects http, credentials, query, IPs, localhost, private names, too long) — tests.
- AC3 — Changing the URL deletes the key in the same batch; a key encrypted for URL A fails to decrypt for URL B — tests.
- AC4 — Chat works end to end with a custom provider and a fake fetch; the request goes only to the configured URL — test.
- AC5 — No key in any output; boundary tests green; the migration is expand-only (guard test green).

## Out of scope
New widget operations, code generated by the model, keys in chat.
