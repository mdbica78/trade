# US-045 — Chat capability: add, update, clear, replace widgets; several actions per message
> Detailed by agent (story-planner), 2026-10-02 — PO to confirm at demo.

**Sprint:** 11 · **Epic:** EPIC-08 · **Depends on:** US-043, US-044, US-040, US-041, US-042
**Suggested model / thinking:** strong model, high thinking. Complex (new capability, shared intent
contract, validation-before-execution and ordered partial-runtime reporting).

## Context

FR18 requires the chat to create, update, clear and replace saved widget definitions without
producing code. FR17 requires the supported-request instruction area in Romanian and English.
DEC-022 §§6–7 replaces the former one-action/refusal behavior with a shared list of 1–5 actions
across capabilities. The approved Sprint 11 review requires inventorying and deliberately migrating
all old single/multiple-intent assumptions. Sprint 10 US-040–042 provide provider/model setup and
the instruction surface; this story integrates with them but does not modify their key storage or
provider presets.

## Task

Add the widget capability under `lib/ai/capabilities/widgets/` with the closed `widget_add`,
`widget_update`, `widget_clear` and `widget_replace` actions. Parse structured JSON and validate
every action against current ETF/catalogue/configuration state before any writes. Update the shared
intent and execution path for ordered lists of up to five actions across all capabilities, including
per-action runtime outcomes. Update the supported-request text in both locales. All provider
responses are mocked in tests; use fake keys only.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1 — Closed widget capability.** The capability registers exactly the supported add, update,
  clear and replace widget actions and parses the expected structured JSON shapes. Each definition
  passes the single `lib/config/widgets.ts` validation/write boundary from US-043; unknown
  operations/fields, unsupported properties and malformed model output become closed errors, not
  writes or uncaught exceptions. Tests cover valid and invalid forms for all four actions.
  (FR18; DEC-022 §§4, 6)
- **AC2 — Safe model boundary.** Model output is parsed as structured data and never executed,
  evaluated as a formula, or rendered as HTML. The model receives only the ETF symbols and the
  field-catalogue labels needed for the request, not provider keys or unrelated stored data.
  Boundary/context tests use mocked providers and assert the supplied context; no live provider or
  real key is used. (FR18; DEC-022 §6; DEC-017)
- **AC3 — Shared action-list contract.** The shared intent result represents 1–5 ordered actions
  across capabilities (not a widget-only list) and replaces the former `{kind: "multiple"}` refusal
  for supported multi-action requests. Requests exceeding five receive the fixed split-the-request
  refusal. Inventory existing exact single/multiple-intent tests and update only assertions whose
  behavior changes under DEC-022; retain regression coverage for a single action and the over-limit
  refusal. (FR18; DEC-022 §7; Sprint 11 review, “Intent/test migration”)
- **AC4 — Validate all before writes.** Before executing any action, validate every action against
  current configuration and catalogue state. If any action is invalid, execute none and identify
  the invalid action in the response. Tests include a valid earlier action followed by an invalid
  later action and assert zero write calls, as well as an all-valid multi-action case.
  (FR18; DEC-022 §7)
- **AC5 — Ordered execution and runtime failures.** For an all-valid list, execute actions in
  input order through their existing capability/config functions. Stop after a runtime failure;
  report each action as `done`, `failed`, or `not run`, and do not claim rollback of already
  completed actions. Tests assert call order and the per-action statuses for success, failure and
  actions after failure. Each individual configuration write remains atomic and widget replacement
  is atomic within its own write. (FR18; DEC-022 §§5, 7)
- **AC6 — Existing configuration capability composes.** The list can contain actions from the
  existing configuration capability and the widget capability in one request; validation of the
  complete list precedes all writes, and mixed valid actions execute in the stated order. Tests use
  fake dependencies and prove both mixed success and mixed-list validation failure with no writes.
  (FR18; DEC-022 §7)
- **AC7 — Localized supported-request instructions.** The existing chat instruction area lists
  supported widget requests and the multi-action behavior in Romanian and English, consistent with
  the actual closed operations and five-action cap. Locale tests assert required keys/text are
  present in both message catalogues. Do not modify or duplicate Sprint 10 key-storage, preset, or
  model-picker behavior. (FR17–FR18; DEC-022 §6–7)
- **AC8 — Offline regression and scope.** All AI-path tests use fake providers and obvious fake
  keys; no live AI, Neon, Vercel or BVB requests occur. Existing one-action configuration behavior
  remains covered, action/server boundaries contain no SQL, and typecheck, lint, focused tests,
  full tests and offline build pass. The implementation stays catalogue-only and makes no raw-field
  or PDF-extraction change. (FR18–FR19; DEC-016; DEC-022 §§7, 9; DEC-023)

## Out of scope

Sprint 10 provider key storage, provider presets, model picker and instruction-area foundation;
widget schema/config functions (US-043); widget evaluation/detail rendering (US-044); raw-field
implementation or extraction changes (US-046 is a spike only); actions beyond the DEC-022 closed
set; cross-action rollback; live AI/provider credentials.
