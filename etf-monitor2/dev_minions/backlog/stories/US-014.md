# US-014 — Missing report, parse failure, and no-adapter handling
> Detailed by agent (story-planner), 2026-09-24 — PO to confirm at demo.

**Sprint:** 3 · **Epic:** EPIC-03 · **Depends on:** US-012
**Suggested model / thinking:** mid model, medium thinking. Complex (DB writes, 9 ACs), so it is planned by `story-planner`.

## Context

EPIC-03 is done when "failures are visible rather than silent". The requirements fix three rules for the non-happy paths:

- **Missing or delayed report** → "that day remains blank in the history (no value) — no automatic retries, no alert" (FR4.1).
- **No adapter** → "the ETF is still shown in the list … but automatic extraction is marked 'unavailable'" (section 3). The admin panel "only flags that an adapter is missing" (section 5, FR13).
- **Parsing errors** must be visible (FR13 "parsing errors (especially useful for ETFs without a matching adapter)"), and a value is never guessed (AGENTS.md).

The data model gives `reports.status` the values `ok | missing | parse_error | no_adapter`. It says FR4.1 "is satisfied by simply having no `ok` row for that date. A `missing` row is optional bookkeeping, never a retry trigger." `reports.report_date` is NOT NULL and means "the date the report is **for**". Only the PDF provides that date (FINDINGS trap 2).

US-012 returns a failure outcome on every non-happy path and writes nothing. This story defines the outcome vocabulary, decides which failures get a `reports` row, and makes the adapter step stricter.

## Task

1. **Outcome vocabulary**, e.g. `lib/ingestion/outcome.ts`. Every `ingestEtf` result is exactly one of:

   | code | when | `reports` row |
   |---|---|---|
   | `ok` | complete result stored (US-012) | `ok` + values |
   | `already_ingested` | an `ok` row already exists for that date (US-012) | none written |
   | `missing` | discovery `not_found`. `detail` distinguishes `no_report_entries` from `list_not_found` (Sprint 2 audit N2) | none (decision 1) |
   | `fetch_error` | discovery or download `http_error` / `network` / `timeout`, or download `not_pdf`. `detail` carries the kind, the HTTP status if any, and the message | none (decision 1) |
   | `no_adapter` | `adapter_key` is NULL or not registered | none (decision 1) |
   | `parse_error` | unreadable text, the assigned adapter's `canHandle` is false, adapter `ok: false`, contract violations, or an incomplete extraction | a `parse_error` row **only when the report date is known** (step 3); otherwise none |
   | `persist_error` | the database write failed | none (atomic write, DEC-010) |

   Each outcome carries the symbol, the code, a one-line human-readable `detail`, and `reportDate` when known. Codes are stable identifiers, because US-015 writes them to the log and US-024 will translate them (FR8.1).
2. **No adapter.** Resolve the adapter **before** any network call. With no adapter, return `no_adapter` without a discovery request or a download. Whether a no-adapter ETF's report link is still discovered and stored for display is US-030 (section 3 "with a link to its report"). This story does not do it.
3. **Parse failures.**
   - Unreadable text, the assigned adapter's `canHandle(text)` returning false (report format changed or wrong adapter; section 3 "match … by report structure"), or adapter `ok: false`: no report date is known, so no row is written (decision 1). The outcome is `parse_error` with the reason.
   - Adapter `ok: true` but **incomplete**: a persisted field is missing, as defined by US-012's selection function. Write one `reports` row with `status = 'parse_error'`, the PDF's `report_date`, `source_url`, `fetched_at`, and an `error_message` that names the missing field keys. Also store the values that **were** found for the other persisted fields (decision 2). Use the same atomic write as US-012 (DEC-010 note 2). The outcome is `parse_error`.
   - Adapter `ok: true` with **contract violations** (`validateExtractionResult` not empty): write a `parse_error` row as above if the report date is itself valid, but store **no** values, because they cannot be trusted. `error_message` lists the violations. If the date is invalid, write no row.
4. **Precedence with existing rows**, extending US-012 step 4:
   - an existing `ok` row for that date is never downgraded: the outcome is `already_ingested` and nothing is written;
   - an existing `parse_error` row for that date is replaced by a later complete result (US-012), or by a later `parse_error` result, whose values replace the old ones.
5. **Messages.** `detail` / `error_message` are short, stable-prefixed English diagnostics (for example, `missing fields: nav_per_unit`). They are not UI strings. They never contain page or PDF content beyond the field keys and the adapter's own error text, and never any environment value.
6. **Tests**: one per row of the table in step 1, plus the step 3 and 4 cases. Use a mocked `fetch`, synthetic HTML/PDF-text inputs or the committed fixtures, and a fake store. No live network, no Neon.

## Acceptance criteria

- **AC1** — No adapter. An ETF with `adapter_key` NULL, or with a key not in the registry, gives `no_adapter`. `fetch` is never called, nothing is written, and an ETF processed after it is unaffected. (Section 3 "extraction is marked 'unavailable'"; FR13; data model `etfs.adapter_key` NULL = no adapter matched; AGENTS.md "No matching adapter → … 'unavailable'. Never guess a value.")
- **AC2** — Missing report. Discovery `not_found` gives `missing`, and its detail distinguishes `no_report_entries` from `list_not_found`. No row, no value, exactly one discovery request, no download. (FR4.1 "blank … no automatic retries, no alert"; data model note on `missing`; Sprint 2 audit N2)
- **AC3** — Fetch failures. Discovery or download `http_error` (with its status), `network`, `timeout`, or download `not_pdf` each give `fetch_error` with that kind in the detail. No row. Each request is made once. (FR4.1; FR13)
- **AC4** — Unusable report. Unreadable text, `canHandle` false for the assigned adapter, or adapter `ok: false` gives `parse_error`, with no row written and no value stored. A test proves that `canHandle` false stops extraction even when `extract` would have returned values. (FR13 "parsing errors"; section 3; data model `reports.report_date` NOT NULL; AGENTS.md "Never guess a value")
- **AC5** — Incomplete extraction. When the report date is known but a persisted field is missing:
  - exactly one `reports` row is written with `status = 'parse_error'`, the PDF's report date, `source_url`, `fetched_at`, and an `error_message` naming every missing field key;
  - the found values of the other persisted fields are stored, and the missing field has no `report_values` row;
  - the write is atomic (DEC-010 note 2);
  - no `ok` row is ever written for an incomplete result.

  (FR4; FR4.1 "no value"; FR13; decision 2)
- **AC6** — Contract violations with a valid date → a `parse_error` row whose `error_message` lists the violations, and no `report_values`. With an invalid date → no row. Either way the outcome is `parse_error`. (FR13; US-009 contract; AGENTS.md "Never guess a value")
- **AC7** — Precedence:
  - an existing `ok` row is never overwritten by a later `parse_error` or partial result for the same date, and the outcome is `already_ingested`;
  - an existing `parse_error` row is replaced by a later complete result (`ok`, correct values) or by a later `parse_error` result (new values and message).

  (US-003 AC2; FR4; FR13)
- **AC8** — Every `ingestEtf` call returns exactly one outcome from the table in Task 1, with symbol, code and detail, and never throws. Across the whole pipeline, the only `reports.status` values written are `ok` and `parse_error` (decision 1). A test enumerates the codes, and a test per code proves its trigger. (FR13; data model `reports.status`)
- **AC9** — `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. (AGENTS.md Commands)

## Out of scope

- Writing outcomes into `job_runs` (US-015).
- Any UI for "unavailable" or for parse errors (Sprint 4 home table; US-024 dashboard; US-030 end to end).
- Discovering or storing a report link for no-adapter ETFs (US-030).
- Assigning an adapter to a newly added ETF, e.g. with `registry.detect` (admin/chat add flows, Sprints 5/6).
- Retries, alerts, notifications (FR4.1; section 6).
- ICBETNETF (US-029).

## Decisions needed

1. **TECHNICAL — failures with no known report date.** `reports.report_date` is NOT NULL and is "the date the report is **for**". For `missing`, `fetch_error`, `no_adapter` and date-less `parse_error` there is no such date.
   - A: write no `reports` row. The outcome is recorded in the `job_runs` log (US-015). "Last successful extraction per ETF" (FR13) stays derivable from the `ok` rows. The `missing` and `no_adapter` status values stay unused for now. The data model already calls a `missing` row "optional bookkeeping".
   - B: write a row keyed on the run's calendar date. This contradicts the column's meaning, would sit one day off the real report dates (FINDINGS trap 2), and can collide with a real report for that date.
   - C: add a per-run, per-ETF results table. This is a schema change and a migration, which US-024 might want for a structured dashboard, but no Sprint 3 criterion needs it.
   - Recommendation: **A**. It needs no schema change, uses no fake dates, and is reversible. If US-024 needs structured per-ETF run history, it can propose C then. For the in-loop `tech-lead` to settle.
   - **Decided: A** — tech-lead sprint review 2026-09-24 (`verification/SPRINT-03-review.md`). B breaks `reports.report_date`'s meaning (FINDINGS trap 2) and can collide with a real report; C is a schema change no Sprint 3 criterion needs. FR13's "last successful extraction" stays derivable from `ok` rows, and date-less failures stay visible through US-015's per-ETF log lines with stable codes.
2. **TECHNICAL — partial extraction: keep the found values?** The Sprint 2 notes left "how a partial extraction maps onto `reports.status`" to this story.
   - A: `parse_error` row, found values stored, missing fields named in `error_message`.
   - B: `parse_error` row with no values (all or nothing).
   - Recommendation: **A**. A correctly extracted value is never thrown away, the row is still flagged, and nothing is guessed. Sprint 4 decides whether values under a `parse_error` row are displayed (sprint-03.md forward note). For the in-loop `tech-lead` to settle.
   - **Decided: A** — tech-lead sprint review 2026-09-24 (`verification/SPRINT-03-review.md`). Storage only: each stored value was extracted by its own label rule, and the row status keeps it out of any "ok" reading. Whether such values are *displayed* stays a Sprint 4 product question.

## Notes for verification

- The reviewer should check that no path turns an unknown date into a guessed one. That means no `new Date()`, no discovery `publishedAt`, and no PDF file-name date used as `report_date`.
- `canHandle` false for the assigned adapter is deliberately a `parse_error`, not a fallback to `registry.detect`. Switching adapters silently would be a guess (section 3; US-009 AC2 "never fall back to another adapter").
- "Incomplete" uses US-012's selection rule: tracked fields, unless PRODUCT decision 1 in US-012 changes it to every extracted field. The tests should build on that function, not duplicate its rule.
- FR4.1 also forbids alerts. Nothing in this story notifies anyone. Visibility is the data, plus the run log from US-015.

## Tech-lead review 2026-09-24

Two points the plan must handle. Neither changes scope.

1. **This story deliberately supersedes part of US-012.** US-012 AC3 ("incomplete … nothing is written") and AC7 ("validation violations, incomplete extraction … the store's write method is never called") describe US-012's interim behaviour. AC5 and AC6 here replace them for the incomplete and contract-violation (valid date) paths. Updating those US-012 tests to the new expected behaviour is a specified behaviour change, not weakening a test (AGENTS.md "Never"). The plan must list each US-012 test it changes and the AC here that replaces it, and the reviewer checks that list. Every other US-012 failure path still writes nothing.
2. **"An `ok` row is never downgraded" (AC7) must also hold inside the write, not only through `findReport`.** Two overlapping runs (a manual trigger during the scheduled one, US-015 notes) can pass `findReport` before either writes. So the `parse_error` save must be a no-op in SQL when an `ok` row already exists for `(etf_id, report_date)`. For example, use `ON CONFLICT … DO UPDATE … WHERE reports.status <> 'ok'`, and scope the values delete/insert to a report id resolved **with** that status condition. With DEC-010 pattern (a), a values insert whose `report_id` subquery ignores status would delete and replace an `ok` row's values even though the upsert was skipped. A test (fake store asserting the condition, `.toSQL()`, or PGlite) shows the guard is present.
