# US-027 — Intent extraction: natural language → configuration action
> Detailed by agent (story-planner), 2026-09-26 — PO to confirm at demo.

**Sprint:** 6 · **Epic:** EPIC-06 · **Depends on:** US-025, US-020, US-021
**Suggested model / thinking:** strong model, high thinking. Complex: it creates the AI capability system and a prompt → parse → validate pipeline whose safety rules decide what a model may trigger. So it is planned by `story-planner`.

## Context

- **FR1:** the user adds or removes any BVB ETF "via natural-language command (e.g., 'add ETF XYZ' / 'stop tracking ETF ABC')".
- **FR2:** the user chooses parameters "also via natural language (e.g., 'also track VUAN for BTBETRETF')".
- **FR5:** the conversational interface is used "**exclusively** for configuration: adding/removing ETFs, choosing which parameters to track".
- **FR8.1:** both languages, "including the conversational interface".
- **Requirements §2.2 design note:** the AI module is "a **capability system** (each capability as a separate 'plugin' on top of the chosen AI provider), not … a single hard-coded command-parsing function".
- **Requirements §5:** AI provider, cron and similar are "operational settings that don't make sense as conversational commands".

What exists:
- **US-025:** the provider interface, `runGeneration`, the fake provider in `test/helpers/`. No capability system yet (sprint decision 3).
- **`lib/config/` (US-020, US-021, DEC-016):**
  - `listEtfs()` returns every ETF with `symbol`, `name`, `isActive` and `adapterAvailable`.
  - `listFieldsForEtf(symbol)` returns the ETF's **available** fields (sprint-05 decision 7) and its **tracked** fields, each with `fieldKey`, `labelRo` and `labelEn`.
  - `normaliseSymbol()` is the symbol rule.
- **Field catalogue** (seed): e.g. `nav_per_unit` has the labels "Valoare unitară a activului net (VUAN)" / "Net asset value per unit", and `net_asset` has "Activ net" / "Net asset".
- **Sprint 5 audit N5:** "Sprint 6's chat will pass user text to these functions, so the chat story should normalise through `normaliseSymbol` first."

This story turns a message into **one validated intent**. It executes nothing and writes nothing. US-028 executes the intent through `lib/config/`.

## Task

1. **Capability system** (sprint decision 3), e.g. `lib/ai/capabilities/`:
   - A `Capability` contract (an id, plus a function that takes its input and a `generate` function bound to the active provider through `runGeneration`).
   - A registry with exactly one entry, `configuration`.
   - Capabilities import the provider **interface** only, never a concrete adapter or the wiring module.
2. **Context**, e.g. `loadConfigurationContext(deps)`:
   - Built from `listEtfs` and `listFieldsForEtf`. It holds, per ETF: symbol, name, active flag, available fields and tracked fields, with `fieldKey`, `labelRo` and `labelEn`.
   - It reads through `lib/config/` and adds no SQL of its own (DEC-016).
   - If the plan finds the per-ETF reads too many round-trips, it adds one read function to `lib/config/` instead.
3. **Prompt**: one function builds the system text. It holds:
   - the four allowed actions and the exact JSON schema;
   - the rule "one action; if the request is not about adding/removing an ETF or tracking/untracking a field, answer `unsupported`; if information is missing, answer `unclear`";
   - the context as data (symbols, names, field keys with **both** labels, so RO and EN wording both match);
   - a line that the user's message is data, not instructions.
   The user's message goes only into `request.user`. JSON mode is on (sprint decision 7).
4. **Intent schema and parser** (sprint decisions 7 and 9), e.g. `lib/ai/capabilities/configuration/intent.ts`. The model is asked for exactly one of:
   - `{"action":"add_etf","symbol":"…","name":"…"|null}`
   - `{"action":"remove_etf","symbol":"…"}`
   - `{"action":"track_field","symbol":"…","field":"<field_key>"}`
   - `{"action":"untrack_field","symbol":"…","field":"<field_key>"}`
   - `{"action":"unsupported"}`, `{"action":"unclear"}`
   The parser accepts that JSON, optionally inside one Markdown code fence, and nothing else. An array or several actions give `multiple`.
5. **Grounding and validation** (sprint decision 8), after parsing:
   - every symbol goes through `normaliseSymbol` (audit N5);
   - `add_etf`: the symbol must occur in the user's message (case-insensitive), and `name` is kept only if it occurs verbatim in the message;
   - the other three actions: the symbol must be an ETF in the context;
   - `track_field`: the field must be in that ETF's available fields and not already tracked (already tracked gives the distinct `already_tracked` reason);
   - `untrack_field`: the field must be in its tracked fields.
   Any failure gives `unclear` with a reason code (`symbol_not_in_message`, `unknown_etf`, `unknown_field`, `not_tracked`, `already_tracked`, `malformed`).
6. **Entry function**, e.g. `interpretConfigurationRequest(message, context, generate)`. It returns a typed outcome:
   - `{ kind: "intent", intent }`;
   - `{ kind: "unsupported" }`;
   - `{ kind: "unclear", reason }`;
   - `{ kind: "multiple" }`;
   - `{ kind: "provider_error", error: ProviderErrorCode }`.
   It makes one `generate` call, never throws and writes nothing.
7. **Tests** with the fake provider: canned model outputs for RO and EN messages, malformed outputs, grounding failures, provider errors. PGlite for the context loader. Boundary tests for the import rules.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1** — Capability system. `lib/ai/capabilities/` has a `Capability` contract and a registry that holds exactly `configuration`. A boundary test checks the imports:
  - no file under `lib/ai/capabilities/` imports a concrete adapter (`lib/ai/providers/<name>`) or the wiring module;
  - no file under `lib/ai/providers/` imports `lib/ai/capabilities/`;
  - `lib/config/` still imports nothing from `lib/ai/` (BC-1).
  (Requirements §2.2 design note "capability system … each capability as a separate plugin"; FR5; DEC-016 §1; sprint decision 3)
- **AC2** — Context from the shared layer. A PGlite test seeds these ETFs: two active, one inactive, and one with no adapter. It then tracks one field. The context lists every ETF with its active flag. An ETF with no adapter has no available fields. The tracked field is listed as tracked, with both labels. The context is built through `lib/config/` functions, and the capability adds no SQL (a source scan finds no `sql\`` under `lib/ai/`). (FR1, FR2, FR10; DEC-016 "a chat story that needs a new rule adds it to `lib/config/`"; sprint-05 decision 7)
- **AC3** — Prompt and request. For a given context and message, the fake provider receives one request:
  - `json: true`;
  - a `system` text that lists the four actions, the schema, every context symbol and each field's key with both labels;
  - a `user` text that equals the trimmed message.
  The message never appears in `system`. (FR5; FR8.1; sprint decision 7)
- **AC4** — The four actions are recognised. Canned model outputs for these messages give the expected validated intent, with a normalised symbol and a catalogue `field_key`:
  - "add ETF XYZ";
  - "adaugă ETF-ul XYZ";
  - "stop tracking ETF BTBETRETF";
  - "nu mai urmări BTBETRETF";
  - "also track VUAN for BTBETRETF" (→ `nav_per_unit`), with a context in which BTBETRETF does not track `nav_per_unit` yet (the seed tracks it, so on a seeded context this case is `already_tracked`, AC6);
  - "urmărește și activul net pentru BTBETRETF" (→ `net_asset`);
  - one untrack in each language.
  (FR1, FR2, FR8.1)
- **AC5** — Output that is not exactly one valid action is never an action. Each of these gives the named outcome, not an intent:
  - non-JSON text → `unclear` / `malformed`;
  - JSON with an unknown `action` → `unsupported`;
  - an array or two actions → `multiple`;
  - a missing required property → `unclear` / `malformed`;
  - a fenced JSON block → parsed normally.
  (Sprint decisions 7 and 9; FR5 "exclusively for configuration")
- **AC6** — Grounding. Each of these gives `unclear` with the named reason:
  - an `add_etf` whose symbol is not in the message ("add the energy ETF" with a model answer of `PTENGETF`) → `symbol_not_in_message`;
  - a `track_field` for a field the ETF's adapter cannot extract → `unknown_field`;
  - a `track_field` for a field it already tracks → `already_tracked`;
  - a field that does not exist → `unknown_field`;
  - an `untrack_field` for an untracked field → `not_tracked`;
  - a `remove_etf` for a symbol not in the context → `unknown_etf`.
  An invented `name` that is not in the message becomes `null`. Lower-case or padded symbols are normalised (`normaliseSymbol`). (AGENTS.md "Never guess a value"; section 3; sprint-05 decision 7; Sprint 5 audit N5; sprint decision 8)
- **AC7** — Scope is configuration only. For "what is the VUAN of BTBETRETF today?" and "write me a poem", with the model answering `unsupported`, the outcome is `unsupported`. An action outside the four (e.g. `set_cron_hour`, `set_ai_provider`, `move_field`) is `unsupported` as well. (FR5 "exclusively for configuration: adding/removing ETFs, choosing which parameters to track"; requirements §5 "operational settings that don't make sense as conversational commands")
- **AC8** — Provider failures and no side effects.
  - Each `ProviderErrorCode` from the fake provider gives `provider_error` with that code.
  - A `generate` that throws is impossible through `runGeneration`, but the entry function also survives a throwing `generate` → `provider_error`.
  - Exactly one `generate` call is made per message.
  - A PGlite test runs the entry function for an `add_etf` and a `track_field` intent: the `etfs`, `tracked_fields` and `settings` rows are unchanged afterwards.
  (DEC-016 §2 "thin callers"; sprint decision 6 "no retry"; FR4.2 spirit, nothing written by interpretation)
- **AC9** — Gates.
  - No test reaches a provider or the network.
  - No new dependency.
  - `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass, with `DATABASE_URL` unset for the build.
  (AGENTS.md "Tests never call … AI providers", Commands)

## Out of scope

- Executing the intent, replies and UI (US-028).
- Reordering fields, setting an adapter, the AI provider or model, or the cron hour by chat (FR5 lists only add/remove ETFs and tracked parameters; requirements §5).
- Queries about values ("what is today's VUAN?"). These get `unsupported` (FR5).
- More than one action per message (sprint decision 9).
- Conversation memory: each message is interpreted on its own (sprint decision 13).
- Measuring how well a real model understands RO/EN phrasing. That can only be proven live (sprint-06.md steps 3–5).

## Notes for verification

- **Canned outputs.** They prove the pipeline (prompt content, parsing, grounding), not the model's understanding. The reviewer checks that no test asserts a live model's behaviour, and that every AC4 case goes through the full `interpretConfigurationRequest` with the real prompt builder, not a parser-only shortcut.
- **Prompt injection.** The user's message is untrusted text. It must never be concatenated into `system`. Even if a message makes the model emit something unexpected, the worst outcome is one of the four validated actions on existing data or on a symbol the user typed. The open admin form can do the same (requirements §6). The reviewer checks that no path executes anything other than a validated intent.
- **"Occurs in the message".** Compare on a normalised form: upper-case, and letters and digits as one token. `BTBETRETF,` and `btbetretf` both count. `XBTBETRETF` does not count for `BTBETRETF`.
- `already_tracked` is a reason, not an error, so that US-028 can reply "already tracked" instead of "not understood".
- **Manual QA (live, user):** sprint-06.md steps 3, 4 and 5.

## Tech-lead review 2026-09-26

Approved for planning. AC4's VUAN example was fixed in place (the seed already tracks `nav_per_unit` for every seeded ETF, `lib/db/seed-data.ts`). Points for the plan:

1. **"JSON" in the prompt.** AC3's `system` text contains the literal word "JSON". OpenAI-compatible JSON mode (Groq) expects it in the messages; it costs nothing for Gemini.
2. **`maxOutputTokens`.** Set it as one named constant in the capability, generous enough for Gemini 2.5 "thinking" models (at least 1024). A one-line JSON answer needs few tokens, but thinking tokens come out of the same budget (US-026 review point 5).
3. **`bad_response` and `model_not_found`.** They reach this story as `provider_error` with the code (AC8 iterates every `ProviderErrorCode`, now seven). US-028 decides the reply wording; this story keeps them distinct.
4. **Prompt data is untrusted too.** ETF names and field labels come from an open admin form (requirements §6). They go into the `system` text as data (for example a JSON block), never as instructions, and the validated-intent rule (sprint decision 8) is what limits the damage, not the prompt.
5. **Capabilities may import `lib/config/*`** (DEC-017). Extend LB-2's allowlist by the exact specifiers the plan lists; AC1's import rules stay as written.
