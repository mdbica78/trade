# US-040 — Store provider keys from `/admin/ai` (write-only, encrypted; DEC-021 decided, key derived from the existing `CRON_SECRET`, no user step)
> Detailed by agent (story-planner), 2026-10-02 — PO to confirm at demo.

**Sprint:** 10 · **Epic:** EPIC-08 · **Depends on:** US-022 (AI settings/key status), US-025 (provider interface and wiring), US-026 (Gemini/Groq adapters), US-028 (chat path), US-048 (deploy-applied migrations, DEC-023)  
**Suggested model / thinking:** strong model, high thinking. This changes the AI secret boundary, crypto/storage lifecycle, provider wiring and `/admin/ai`, with a migration and multiple privacy-critical criteria.

## Context

- **FR16** requires entering/replacing a provider key from `/admin/ai`, write-only, never shown again, and stored encrypted. The user's accepted no-login risk is settled by DEC-021; do not reopen it.
- **DEC-021** specifies the `ai_provider_keys` table, AES-256-GCM format, per-write 12-byte random IV, provider ID as authenticated additional data, `key_source`, key derivation precedence, key validation, stored/environment/unset precedence, write-only UI, closed errors, module boundary, same-origin action mitigation, `robots: noindex`, and safe handling of missing tables/read failures.
- **DEC-023** requires a locally generated, expand-only migration applied by production build. Tests prove the migration with PGlite; agents never run it against Neon.
- **Sprint 10 pre-detail review §2–3** adds minimum evidence for async provider wiring, master-key rotation/source behavior, missing-table health visibility, and leak scans. No key may cross out of `lib/ai/`.
- All code/test fixtures use obvious fake keys only. `AI_KEY_MASTER_KEY`, `CRON_SECRET`, derived keys, plaintext, ciphertext and `ai_provider_keys` rows are secrets and are never read from the real environment/database, logged, selected, seeded, printed, or included in artifacts.

## Task

1. Add `ai_provider_keys` as its own table and expand-only migration, matching DEC-021 exactly; update migration metadata and any schema-table inventory/health probe needed to identify the missing table without reading its rows.
2. Implement encryption/decryption and key derivation under `lib/ai/key-store.ts`, obtaining environment material only through the existing `lib/ai/key-status.ts` boundary. Persist the DEC-021 ciphertext encoding, source marker and timestamp. Preserve the specified provider-ID AAD and source-based decryption behavior.
3. Add `lib/config/ai-keys.ts` save/clear functions using the existing configuration write pattern and injected encrypt/store dependencies. Keep the Server Action thin; validate provider/key/storage-enabled state and return only closed, key-free results.
4. Make provider-key loading asynchronous at the outer edge in `lib/ai/provider-deps.ts`; keep `resolveActiveProvider` synchronous and unchanged. Update `/admin/ai` to show key-free status/source, write-only input and clear action. Inside `lib/ai/`, only `key-status.ts`, `key-store.ts`, and `provider-deps.ts` handle environment or stored key material; only `provider-deps.ts` and `lib/config/ai-keys.ts` import `key-store.ts`. The Server Action receives the submitted key as request input, and `lib/config/ai-keys.ts` may validate and pass it transiently to the injected encryption/store dependency; neither may persist it in plaintext, log it, return it, or include it in any view/result. No plaintext-bearing object leaves the `lib/ai/` provider runtime/wiring path to a caller or client.
5. Preserve missing-table fallback, sanitised per-provider failure logging, same-origin server-action behavior and `robots: noindex` for `/admin` and `/chat`. No rate limiter or login is added.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1 — Dedicated schema and safe migration.** `ai_provider_keys` has exactly the DEC-021 fields (`provider_id` primary key, `ciphertext`, `key_source`, `updated_at`) and no plaintext, key prefix/suffix, or key length column. Its migration is expand-only and registered in journal order. PGlite applies the full migration journal and can insert/read only the expected encrypted row shape. `/health` schema inventory identifies this required table when absent without selecting its contents. (FR16; DEC-021 §§1, 5; DEC-023 §§4–5)
- **AC2 — Encryption and authenticated storage.** Offline crypto tests prove AES-256-GCM round-trip, a fresh random 12-byte IV on every write, rejection after ciphertext/tag tampering, rejection when provider-ID AAD changes, and rejection with the wrong encryption key. The stored representation is base64 of `iv ‖ tag ‖ ciphertext` and contains no plaintext. Crypto modules execute only in Node runtime, not Edge. (FR16; DEC-021 §§1–2)
- **AC3 — Derivation and recorded key source.** Deterministic tests prove HKDF-SHA256 uses salt `etf-monitor2`, info `ai-provider-keys/v1`, outputs 32 bytes, and differs from raw `CRON_SECRET`. A valid 32-byte base64 `AI_KEY_MASTER_KEY` wins for new writes; otherwise a `CRON_SECRET` of at least 24 characters is the fallback; shorter/missing/invalid material disables storage. Each row records `master` or `cron_derived`; old rows continue decrypting by their recorded source when a new master key is configured, while unavailable source or rotated `CRON_SECRET` makes only that stored key unavailable (not a fallback decryption attempt with a different source). All tests use literal fake material, never process secrets. (FR16; DEC-021 §2)
- **AC4 — Key precedence and asynchronous provider wiring.** With mocked DB/environment dependencies, provider resolution chooses stored key before environment key before unset. Stored keys are loaded asynchronously before the existing synchronous `resolveActiveProvider` is called; resolver shape/semantics and provider adapters remain unchanged. A stored-key read/decrypt failure for one provider resolves as no stored key (`no_api_key`) and does not prevent other providers from loading. (FR16; DEC-017; DEC-021 §§4–5)
- **AC5 — Save, replace, clear and closed validation.** PGlite/config tests prove save and replacement upsert encrypted rows, clear deletes only the selected provider's stored row and restores environment-key fallback, and invalid provider, provider not requiring a key, invalid key (trimmed length 8–512, no whitespace/control characters), disabled storage and persistence failure map only to `unknown_provider`, `key_invalid`, `storing_disabled` or `write_failed`. Action success/error results contain no key or ciphertext. A posted `baseUrl` field is ignored and cannot influence provider routing. (FR16; DEC-016; DEC-021 §§6, 8)
- **AC6 — Missing table and failure privacy.** When `ai_provider_keys` is absent, reads return the no-stored-key state so existing settings/ETF reads and `/admin/ai` continue to render. A per-provider read/decrypt error logs one sanitized closed-code/provider-ID line in the DEC-019 style; no raw exception, plaintext, ciphertext, master/derived key, `CRON_SECRET`, URL or environment value appears in logs, thrown messages, rendered HTML or action results. (FR16; DEC-019; DEC-021 §§4, 7; DEC-023)
- **AC7 — Write-only bilingual UI and mitigations.** `/admin/ai` displays only whether a key is set and its source (`stored`, `environment`, `none`), never key material. When storage is disabled, the key input is not rendered; the page shows only the translated disabled note and continues to support environment-variable keys. When enabled, the input is `type="password"`, `autocomplete="off"`, has no default value, and is cleared after save; replacement and “Clear stored key” work. Storage-disabled state is visible without exposing why secret material is invalid. All new strings are localized in Romanian and English. `/admin` and `/chat` send `robots: noindex`; the action relies on the framework's same-origin protection without adding a custom bypass. (FR16; FR8.1; DEC-021 §§3, 6, 11)
- **AC8 — Hard secret boundary.** Boundary tests establish that, within `lib/ai/`, only `key-status.ts`, `key-store.ts`, and `provider-deps.ts` handle environment or stored key material; only `provider-deps.ts` and `lib/config/ai-keys.ts` import `key-store.ts`; no client component or `app/` module imports secret-bearing library modules. The Server Action and `lib/config/ai-keys.ts` may receive the submitted key transiently for validation and pass it to injected encryption/storage, but may not log, persist in plaintext, return, or render it. No plaintext-bearing provider key leaves the `lib/ai/` runtime/wiring path to a caller or client. Leak tests assert the obvious fake key is absent from serialized views, rendered HTML, action results, thrown messages, captured console output and test output. No test reads/selects/seeds a real `ai_provider_keys` row or reads a secret variable. (FR16; DEC-017 §4 as amended by DEC-021 §§5–7, 10)
- **AC9 — Offline gates.** Focused encryption, key-store, config/PGlite, provider-wiring, action, UI, health and boundary tests pass; full `pnpm typecheck`, `pnpm lint`, `pnpm test` and offline `pnpm build` pass with database, Vercel and provider secret variables absent. Migration is generated locally and applied only to PGlite in tests; no live provider, Neon or Vercel operation occurs. (FR16; DEC-021; DEC-023; AGENTS.md “Commands” and “Secrets”)
