# US-043 — Schema, validator and config functions for the widget definition
> Detailed by agent (story-planner), 2026-10-02 — PO to confirm at demo.

**Sprint:** 11 · **Epic:** EPIC-08 · **Depends on:** US-048 (production-build migration path, DEC-023)
**Suggested model / thinking:** strong model, high thinking. Complex (schema/migration, closed validation
and atomic configuration writes); plan with `story-planner`.

## Context

FR18 defines saved derived values from a closed structured definition, never code. DEC-022 §§1, 3–5
settles the definition, schema, single validation gate, write functions and isolated defaults. The
approved Sprint 11 review binds the implementation to existing numeric `field_catalog` entries and
requires a separate expand-only `etf_widgets` migration. DEC-023 means migrations are generated and
tested locally, then applied by the production build; an agent never runs them against Neon.

## Task

Add the typed `etf_widgets` table and its own migration with the DEC-022 columns and constraints:
serial id; cascading ETF FK; slot 1–6; closed operation and period-unit checks; integer period amount
1–365; optional title; updated timestamp; unique `(etf_id, slot)`. Keep widget definitions in
columns, not JSON. Add `lib/config/widgets.ts` as the sole definition validator and widget
configuration-write layer, following DEC-016's `Db` + `BatchRunner` pattern. Export validation and
configuration functions for add, update, clear-one/clear-all, and atomic replace. Generate the
migration with project tooling and test it on PGlite only.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1 — Persisted closed schema.** The `etf_widgets` table has precisely the definition/storage
  columns and constraints specified by DEC-022 §3: operation is one of `change`, `percent_change`,
  `average`, `min`, `max`; period unit is `days` or `reports`; slot is 1–6; amount is 1–365;
  `(etf_id, slot)` is unique and ETF deletion cascades. Definitions are not stored as JSON.
  Schema tests and PGlite constraint tests exercise valid rows and each rejected boundary/duplicate.
  (FR18; DEC-022 §3)
- **AC2 — Expand-only migration path.** The table is introduced by its own generated migration, and
  the migration applies successfully to an empty PGlite database in journal order with the expected
  table, FK, uniqueness and checks. Do not run `db:migrate`, `drizzle-kit migrate`, or the deploy
  script against a real database. (FR18; DEC-022 §3; DEC-023 §§4–5)
- **AC3 — One closed validation gate.** `validateWidgetDefinition(input, catalogue)` accepts only
  the five operations and two period units, an integer amount 1–365, an optional plain-text title
  no longer than 60 characters, and a field key in the supplied ETF adapter catalogue whose
  catalogue entry is numeric. Reject unknown keys rather than ignoring them; reject expressions,
  formulas, code, URLs, free-form field names and non-numeric/unknown fields. Invalid model-shaped
  inputs return the settled closed error codes (`unknown_operation`, `unknown_field`, `bad_period`,
  `bad_title`, `bad_slot`, `unknown_etf`, `too_many`) and do not throw. Table-driven unit tests
  cover accepted boundaries, each error code, and malformed/untrusted inputs. (FR18; DEC-022 §§1, 4)
- **AC4 — Add and update operations.** `addWidget` validates then writes to the first free slot,
  returns `too_many` when all six slots are occupied, and does not overwrite an existing slot.
  `updateWidget` validates the supplied changes and changes only supplied fields in the selected
  slot, preserving the rest. Tests cover slot ordering, all-slots-full, invalid input with no write,
  and partial update preservation through PGlite and/or injected write-boundary tests. (FR18;
  DEC-022 §§3–5)
- **AC5 — Clear and replace operations.** `clearWidget` removes only the requested slot, or all
  widgets for that ETF when requested; clearing one ETF never affects another. `replaceWidgets`
  validates the complete replacement list and replaces that ETF's list in one atomic batch, so
  invalid input or a batch failure cannot expose a partial replacement. PGlite tests verify both
  isolation and atomic replacement. (FR18; DEC-022 §5)
- **AC6 — Configuration boundary.** Widget reads/writes and validation are in the config module;
  callers use its typed functions and neither actions nor chat issue SQL of their own. Tests exercise
  the public config API with fake dependencies/PGlite, and a boundary test guards the no-SQL caller
  rule. The catalogue-only validator does not add or infer raw extraction fields. (FR18–FR19;
  DEC-016; DEC-022 §§4–6; Sprint 11 review, “Extraction boundary”)
- **AC7 — Defaults and build gates.** Capacity remains six per ETF, ownership stays per ETF, and no
  user confirmation blocks this work. Typecheck, lint, focused tests, the full test suite and offline
  build pass under project commands; no live Neon/Vercel/provider call or real key is used. (FR18;
  DEC-022 §3 and PW-1; DEC-022 Consequences; DEC-023; Sprint 11 review, “Secrets”)

## Out of scope

Widget evaluation or display (US-044); chat capability or multi-action intent (US-045); global
widgets; different limits or average precision; arbitrary/raw fields, extraction or adapter
changes; backfill of historical reports; user authentication; live migration or deployment.
