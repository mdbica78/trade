# US-025 — Pluggable LLM provider adapter interface
> Detailed by agent (story-planner), 2026-09-26 — PO to confirm at demo.

**Sprint:** 6 · **Epic:** EPIC-06 · **Depends on:** US-022
**Suggested model / thinking:** strong model, high thinking. Complex: it is the core of the AI provider system and it deliberately changes the secrets boundary that US-022 built. So it is planned by `story-planner`.

## Context

FR6: "The user can choose which AI model powers the conversational interface, from a list of integrable free options (the architecture must be 'pluggable' — a single AI-provider adapter, easy to swap)." FR5: the AI is used "exclusively for configuration". Requirements §2.2 design note: the AI module is "a capability system (each capability as a separate 'plugin' on top of the chosen AI provider)". Roadmap carry-forward: "API keys are live steps for the user, never handled by agents."

What exists (US-022):
- **Provider catalogue.** `lib/ai/provider-catalog.ts` is static data: `id`, `name`, `requiresApiKey`, `apiKeyEnvVar`. Its four ids are `gemini`, `groq`, `openrouter` and `mistral`.
- **Key status.** `lib/ai/key-status.ts` is "the only file that reads a provider API key variable". It returns booleans only.
- **Settings.** `lib/config/ai-settings.ts` has `getAiSettings()`, which returns `{ provider, model }` from `settings`. `lib/ai/settings-deps.ts` wires the allowed ids into it, because `lib/config/` never imports `lib/ai/` (DEC-016 §1, `lib/config/boundaries.test.ts`).
- **Boundary tests** (`lib/ai/boundaries.test.ts`):
  - LB-1: the catalogue has no imports.
  - LB-2: `lib/ai` imports only an allowlist and contains no `fetch(`.
  - LB-3: `process.env` appears only in `key-status.ts`.
  - LB-4: only `app/admin/ai/page.tsx` imports `key-status`, and no client component does.
  To call a provider, a key value must reach an adapter and an HTTP request must be made. LB-2 and LB-4 therefore change in this story, as sprint decision 2 rules. They are not dropped.
- No adapter exists yet. The concrete providers are US-026, and the configuration capability is US-027.

## Task

1. **Interface** (sprint decision 1), e.g. `lib/ai/providers/types.ts`:
   - `AiProvider` has `id` and `generate(request, ctx)`.
   - `GenerateRequest` holds `system`, `user`, `json: boolean` and `maxOutputTokens`.
   - `ProviderCallContext` holds `apiKey`, `model`, an injected `fetch` and an `AbortSignal`.
   - `GenerateResult` is `{ ok: true; text: string }` or `{ ok: false; error: ProviderErrorCode }`, where `ProviderErrorCode` is the closed set `timeout | network | auth_failed | rate_limited | model_not_found | provider_error | bad_response` (`model_not_found` added by the tech-lead, 2026-09-26, sprint decision 1).
   - An adapter must never throw, never put the key, the URL or the response body into its result, and make at most one request per call.
2. **Wrapper**, e.g. `runGeneration(provider, request, ctx, { timeoutMs })`:
   - It owns the `AbortController` and the timeout, as one constant in `lib/ai/` (sprint decision 6: 20 s).
   - A timeout returns `timeout`. Anything the adapter throws becomes `provider_error`.
   - It never throws.
   Every caller goes through it.
3. **Provider registry**, e.g. `lib/ai/providers/registry.ts`:
   - `createProviderRegistry(adapters)` gives `get(id)` and `list()`.
   - Construction rejects a duplicate id, and an id that is not in `PROVIDER_CATALOG`. A bad registry is a programming error, so construction may throw here; a unit test covers it.
   - This story ships the registry **empty**. US-026 adds the adapters.
4. **Active-provider resolution** (pure), e.g. `resolveActiveProvider({ settings, registry, readApiKey })`:
   - Success returns `{ ok: true, provider, model, apiKey }`.
   - Otherwise it returns `{ ok: false, reason }`, with `reason` one of:
     - `not_configured`: `ai_provider` is NULL;
     - `unknown_provider`: the id is not in the catalogue (sprint-05 decision 10: "must display as none/unknown, not crash");
     - `not_implemented`: the id is in the catalogue but has no adapter;
     - `no_api_key`: the provider requires a key and its variable is unset or blank;
     - `no_model`: `ai_model` is NULL (sprint decision 4).
   - Checks run in that order. It never throws.
5. **Key value** (sprint decision 2):
   - Add `readApiKey(providerId): string | null` to `lib/ai/key-status.ts`, which stays the only `process.env` reader (LB-3 unchanged). The value goes only into `ProviderCallContext.apiKey`.
   - One server-side wiring module, e.g. `lib/ai/chat-deps.ts`, is the only place that combines `getAiSettings`, `readApiKey`, the registry and the global `fetch`. The plan names it.
6. **Boundary tests** (`lib/ai/boundaries.test.ts`), revised as sprint decision 2 states:
   - LB-1 and LB-3 are unchanged.
   - LB-2: the specifier allowlist still admits no SDK (no `openai`, `@google/*`, `groq-sdk`, `@ai-sdk/*`, `@mistralai/*` …). The blanket "no `fetch(`" is replaced: a network call may appear only in `lib/ai/providers/*` and only through the injected context `fetch`. The global `fetch` is referenced only in the wiring module.
   - LB-4: the importers of `key-status` are exactly `app/admin/ai/page.tsx` and the wiring module, and no client component.
   - Add a check that no type exported for `app/` use (resolution failure, generation result) has a field carrying the key.
7. **Test double:** a fake provider in `test/helpers/` (not shipped code) that records requests and returns scripted results. US-027 and US-028 reuse it.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1** — One adapter interface. `AiProvider`, `GenerateRequest`, `ProviderCallContext`, `GenerateResult` and the closed `ProviderErrorCode` set exist in one module. A fake provider typed against them compiles and passes the wrapper's tests. No type in the interface names a concrete provider. (FR6 "a single AI-provider adapter, easy to swap"; sprint decision 1)
- **AC2** — The wrapper never throws. Tests cover each of these:
  - an adapter that resolves `ok` passes its text through;
  - an adapter that throws gives `provider_error`;
  - an adapter that never settles gives `timeout` once the timeout constant elapses (fake timers), and its `AbortSignal` is aborted;
  - an adapter that returns an error code passes it through unchanged.
  The returned object never carries an exception message. (FR6; AGENTS.md secrets rule; sprint decisions 1 and 6)
- **AC3** — Registry. `get` and `list` return the adapters given. Construction rejects a duplicate id and an id not in `PROVIDER_CATALOG`. The shipped registry is empty in this story, and a test pins that (US-026 changes it). (FR6 "from a list of integrable free options"; sprint-05 decision 10)
- **AC4** — Resolution. One unit test per branch: `not_configured`, `unknown_provider` (e.g. a stored `"foo"`), `not_implemented`, `no_api_key` (unset and blank), `no_model`, and `ok` with a fake adapter registered. The checks run in the documented order. Resolution never throws and makes no network request. (FR6, FR11; sprint-05 decision 10; sprint decision 4)
- **AC5** — Key boundary. `vi.stubEnv` sets every catalogue key variable to a distinct sentinel. Then:
  - `readApiKey` returns the sentinel only for its own provider, and `getKeyStatuses()` still returns booleans only (US-022 AC4 unchanged);
  - for a resolution failure and for a fake adapter that returns an error, the serialised result (`JSON.stringify`) contains no sentinel;
  - the revised LB-4 passes: exactly `app/admin/ai/page.tsx` and the named wiring module import `key-status`, and no client component does;
  - LB-3 passes unchanged.
  (AGENTS.md "Secrets live only in environment variables, server-side. Never commit, log or print one"; DEC-015 point 1; sprint-05 decision 9; sprint decision 2)
- **AC6** — No SDK, network only by injection. The revised LB-2 passes:
  - every `lib/ai` import is on the allowlist, which holds no provider SDK;
  - a network call appears only in `lib/ai/providers/*`, through the context `fetch`;
  - the global `fetch` is referenced only in the wiring module.
  `package.json` gains no dependency. No test reaches the network: the tests use the fake provider or an injected `fetch` mock. (ADR-001; AGENTS.md "New runtime dependency …", "Tests never call … AI providers"; sprint decision 1)
- **AC7** — Nothing else changes, and the gates pass.
  - `/admin/ai` behaves exactly as before, and its existing tests pass unchanged.
  - `lib/config/` still imports nothing from `lib/ai/` (BC-1).
  - There is no schema change and no UI string change.
  - `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. The build also passes with `DATABASE_URL` and every key variable unset.
  (DEC-016 §1; AGENTS.md Commands)

## Notes for verification

- **Changing a boundary test.** Sprint decision 2 authorises the LB-2/LB-4 revision. The reviewer checks three things:
  - the new assertions are at least as strict for everything outside `lib/ai/providers/*` and the wiring module;
  - LB-3 is untouched;
  - no assertion was simply deleted.
  "Weaken a test to make it pass" (AGENTS.md "Never") is exactly what this must not be.
- **Sentinel tests.** Use values like `SENTINEL-GEMINI-7d1e`, set with `vi.stubEnv` and cleared with `vi.unstubAllEnvs`. Never read or print the real environment (DEC-015).
- **Timeout.** Use fake timers for the timeout test. A real 20 s wait is not acceptable in the suite.
- The empty shipped registry means that, after this story alone, resolution returns `not_implemented` for every catalogue id. That is expected. US-026 fills the registry.
- **Manual QA (live, user):** none for this story alone. It is proven live through sprint-06.md steps 2 and 6 once US-026 and US-028 are in.

## Tech-lead review 2026-09-26

Approved for planning. Sprint decisions 1, 2 and 3 are Decided and recorded in `decisions/DEC-017-ai-provider-layer.md`, which binds later AI capabilities. The plan must include these points (they tighten the draft; no AC is loosened):

1. **Error set.** `ProviderErrorCode` includes `model_not_found` (Task 1 updated in place). AC1 and AC2 apply to the full set of seven codes.
2. **LB-4 covers `lib/`.** Today LB-4 (`lib/ai/boundaries.test.ts`) walks only `app/` and `components/`. The revised LB-4 walks `lib/` as well (non-test files), so "exactly `app/admin/ai/page.tsx` and the wiring module import `key-status`" is true of the whole tree, not of two folders. It also asserts that no file under `app/` or `components/` contains `readApiKey`.
3. **The key stays inside `lib/ai/`.** The successful resolution object carries `apiKey`. It is consumed only inside `lib/ai/` (wiring module and, in US-028, the chat entry module). The check in Task 6 ("no type exported for `app/` use … carries the key") names the exported types it covers, and US-028's page gets a key-free availability view, never the resolution object.
4. **"Global `fetch` only in the wiring module" is a concrete scan.** In every non-test file under `lib/ai/` except the wiring module: no bare `fetch(` call (a `fetch(` not preceded by `.`) and no `globalThis.fetch`. In `lib/ai/providers/*` the call is on the context object (e.g. `ctx.fetch(`). Outside `lib/ai/providers/*` and the wiring module, `fetch` does not appear at all. LB-2's specifier allowlist grows only by the new relative module paths the plan lists; it still admits no package other than those already on it.
5. **AC5 sentinel for the success path.** If this story's wiring module exports a key-free availability view (recommended: it sits next to the resolution), one test serialises it for the `ok` case with sentinels set and asserts no sentinel appears. If the plan leaves that view to US-028, US-028 AC7 carries the test.
