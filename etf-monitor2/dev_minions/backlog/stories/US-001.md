# US-001 — Spike: validate PDF text extraction from a BRD depositary report

**Type:** spike (investigation — the deliverable is a decision plus a small proof script, not production code)
**Sprint:** 1 · **Epic:** EPIC-01 · **Depends on:** nothing
**Suggested model / thinking:** strong model, high thinking

## Context

The application extracts financial figures from daily depositary reports published as PDFs on bvb.ro. Three of the ETFs in scope (BTBETRETF, TVBETETF, PTENGETF) share one report template, produced by BRD — Groupe Société Générale. The reports render as crisp vector text, which suggests they are generated programmatically rather than scanned, but this has **not** been verified by actually extracting the text. Everything downstream depends on the answer.

## Task

Determine which Node.js library reliably extracts the numeric fields from these reports, and prove it.

1. Create a folder `spikes/pdf-extraction/` and a `test/fixtures/` folder at the repository root.
2. Download three sample reports (one per ETF) into `test/fixtures/`, naming them `<SYMBOL>-<YYYY-MM-DD>.pdf`. Report links are in the "Știri" section of each instrument page:
   - `https://bvb.ro/FinancialInstruments/Details/FinancialInstrumentsDetails.aspx?s=BTBETRETF`
   - `https://bvb.ro/FinancialInstruments/Details/FinancialInstrumentsDetails.aspx?s=TVBETETF`
   - `https://bvb.ro/FinancialInstruments/Details/FinancialInstrumentsDetails.aspx?s=PTENGETF`
3. Write a standalone script that, for each candidate library, loads each fixture and dumps the extracted text:
   - `unpdf`
   - `pdf-parse`
   - `pdfjs-dist`
4. For each library, check whether these labels and their associated numbers can be located in the extracted text:
   - `ACTIV NET (in valuta fond - RON)`
   - `NUMAR U.F. in circulatie, din care detinute de:` — plus the two indented sub-values (`Persoane fizice`, `Persoane juridice`)
   - `VALOARE UNITARA A ACTIVULUI NET (VUAN) (RON)`
   - `Numar investitori, din care:` — plus its two sub-values
   - the report date, from the header line `Raport depozitar la data de DD.MM.YYYY in valuta RON`
5. Write the findings to `spikes/pdf-extraction/FINDINGS.md`: which library worked, how the numbers appear in the raw extracted text (spacing, separators, whether label and value land on the same line), and any trap discovered.

## Acceptance criteria

- **AC1** — Three real report PDFs are committed under `test/fixtures/`.
- **AC2** — The script runs against all three fixtures for each candidate library without crashing, and prints extracted text.
- **AC3** — `FINDINGS.md` states, for each library, whether every field listed in step 4 is retrievable, with a verbatim excerpt of the extracted text around at least one numeric field.
- **AC4** — `FINDINGS.md` ends with a clear recommendation of one library, and states explicitly whether OCR is needed (yes/no).
- **AC5** — `FINDINGS.md` documents the exact number formatting found in the raw text (thousands separator, decimal separator), because the production parser will depend on it.

## Out of scope

- No adapter, no database, no UI, no production code.
- Do not build a general parser yet — this spike only establishes feasibility and format.
- Do not attempt ICBETNETF: it uses a different report format and a different download mechanism, handled later in Sprint 7.

## Notes for verification

The numbers in these reports are large and separator-heavy (for example a net asset figure in the hundreds of millions, and a units-in-circulation figure in the tens of millions). Getting the separator convention wrong would silently corrupt every stored value, so AC5 is not optional detail — it is the point of the spike.
