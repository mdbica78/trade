# US-004 — Bilingual (RO/EN) infrastructure and language switcher

**Sprint:** 1 · **Epic:** EPIC-01 · **Depends on:** US-002
**Suggested model / thinking:** cheap model, low thinking

## Context

FR8.1 requires the interface to work in both Romanian and English, switchable. This is built now, before any real UI exists, because retrofitting translation keys across a finished interface is significantly more expensive than starting with them.

## Task

1. Add and configure `next-intl` for the App Router, with locales `ro` and `en`, default `ro`.
2. Create message catalogues `messages/ro.json` and `messages/en.json`, with the same key structure in both. Seed them with the keys needed so far: application name, navigation labels, and the health-check page strings that US-006 will use.
3. Persist the chosen locale so it survives a reload (cookie, not browser-local storage — the locale must be readable server-side for rendering).
4. Build a `LanguageSwitcher` component in `components/` that toggles between RO and EN and is placed in the application layout.
5. Establish the convention — documented in the root `README.md` — that **no user-facing string is hard-coded**; every one goes through a translation key. Every later UI story depends on this rule.
6. Write a unit test asserting that `ro.json` and `en.json` contain exactly the same set of keys (recursively). This test is the guard against translations drifting apart as the app grows.

## Acceptance criteria

- **AC1** — The app renders in Romanian by default.
- **AC2** — The language switcher changes all visible labels between RO and EN.
- **AC3** — The selected locale survives a full page reload.
- **AC4** — `messages/ro.json` and `messages/en.json` have identical key structures.
- **AC5** — A unit test fails if a key exists in one catalogue but not the other — verify this by temporarily adding a key to one file and observing the failure before removing it again.
- **AC6** — No hard-coded user-facing strings remain in any component added by this story.
- **AC7** — `pnpm test`, `pnpm lint`, and `pnpm build` all pass.

## Out of scope

- No translation of content that comes from the database (ETF names, field labels) — those carry their own `label_ro` / `label_en` columns and are handled where they are displayed.
- No locale-specific number or date formatting yet; that belongs with the stories that render numbers.
- No additional languages.
