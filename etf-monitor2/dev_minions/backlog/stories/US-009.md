# US-009 — Adapter interface and registry
> Detailed by agent (story-planner), 2026-09-23 — PO to confirm at demo.

**Sprint:** 2 · **Epic:** EPIC-02 · **Depends on:** US-005
**Suggested model / thinking:** strong model, high thinking. Complex (adapter framework), so it is planned by `story-planner`.

## Context

Report formats differ between issuers, and the user can add any ETF listed on BVB. So extraction must be "a system of adapters per report format, not a single rigid parser" (requirements section 3). When a new ETF is added, the system tries to match it to a known adapter "by issuer/depositary or by report structure". If none matches, the ETF is still listed, but extraction is marked "unavailable" (section 3; FR13). Creating a new adapter is development work, not a UI action (section 5).

The data model already carries the key: `etfs.adapter_key` (NULL = no adapter matched) and `field_catalog.adapter_key` (what each adapter can extract, FR10). US-005 seeded `brd-depositary` for the three BRD ETFs and its eight catalogue fields.

This story defines the contract every adapter implements and the registry that maps a key to an adapter. It does this with a fake adapter only. The real BRD adapter is US-010.

## Task

1. **Contract**, e.g. `lib/extraction/adapters/types.ts`:
   ```ts
   interface ExtractionAdapter {
     key: string;                        // = etfs.adapter_key = field_catalog.adapter_key
     fieldKeys: readonly string[];       // every field it can extract (its field_catalog rows)
     canHandle(text: string): boolean;   // report-structure match (section 3)
     extract(text: string): ExtractionResult;
   }
   type ExtractedValue = { fieldKey: string; numericValue: string; rawValue: string };
   type ExtractionResult =
     | { ok: true; reportDate: string /* YYYY-MM-DD */; values: ExtractedValue[]; missingFields: string[] }
     | { ok: false; error: string };
   ```
   - `numericValue` is a canonical decimal string: optional `-`, digits, and optionally `.` plus digits. No thousands separator. It maps losslessly onto `report_values.numeric_value numeric`, which Drizzle reads and writes as a string.
   - `rawValue` is the token exactly as it appeared in the text (`report_values.raw_value`, kept "for auditing", data model).
   - The adapter returns every field it can extract. Choosing which fields to persist is the caller's job (Sprint 3).
   - `ok: false` is for text the adapter cannot use at all, including when no report date is found (`reports.report_date` is NOT NULL). A field that cannot be found goes in `missingFields` and gets no value.
   - The plan may rename things, but must keep these semantics.
2. **Contract check**, e.g. `validateExtractionResult(adapter, result)`, returning a list of violations (empty = valid):
   - every `fieldKey` in `values` is in `adapter.fieldKeys`;
   - no field appears twice;
   - `values` and `missingFields` together cover `fieldKeys` exactly;
   - `reportDate` is a real calendar date in `YYYY-MM-DD`;
   - every `numericValue` has the canonical format.

   US-010/US-011 tests use it, and Sprint 3 ingestion can call it before writing.
3. **Registry**, e.g. `lib/extraction/adapters/registry.ts`:
   - `createAdapterRegistry(adapters)` throws on a duplicate key;
   - the registry exposes `get(key: string | null | undefined)`, which returns the adapter or `undefined`, `list()`, and `detect(text)`, which returns the one adapter whose `canHandle(text)` is true, or `undefined` when none or more than one match;
   - a default app registry is built from the list of real adapters. That list is empty until US-010 adds `brd-depositary`.
4. Unit tests with fake adapters defined in the test file.

## Acceptance criteria

- **AC1** — The contract in Task 1 exists and is exported, with the semantics listed there (report date as `YYYY-MM-DD`; per-field `numericValue` canonical string plus verbatim `rawValue`; `missingFields`; `ok: false` for unusable text). (FR3; FR4; data model `reports.report_date`, `report_values.numeric_value`/`raw_value`)
- **AC2** — `get("<registered key>")` returns that adapter. `get(null)`, `get(undefined)` and `get("unknown-key")` return `undefined`, never throw, and never fall back to another adapter. (Section 3 "extraction is marked unavailable"; data model `etfs.adapter_key` NULL = no adapter; AGENTS.md "Never guess a value")
- **AC3** — `createAdapterRegistry` throws a clear error when two adapters share a key. (Data model: `adapter_key` identifies one format in both `etfs` and `field_catalog`)
- **AC4** — `detect(text)` returns the single adapter that claims the text. It returns `undefined` when no adapter claims it, and also when two or more do: an ambiguous match is not a match. (Section 3 "match … by report structure"; AGENTS.md "Never guess a value")
- **AC5** — `validateExtractionResult` reports a violation for each broken rule in Task 2 (a test per rule), and none for a valid result. (FR4; data model `report_values`; AGENTS.md "Never guess a value")
- **AC6** — The contract and registry modules import no database, network or PDF-library code. Adapters work on text only. Checked by review of the imports. (FR5 deterministic parser; section 3 separation; AGENTS.md architecture rules)
- **AC7** — `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. (AGENTS.md Commands)

## Out of scope

- The BRD adapter itself (US-010).
- Assigning an `adapter_key` to a newly added ETF (admin/chat add flows, Sprints 5/6), and the "unavailable" display (US-030 end to end). This story only provides `get`/`detect` for them.
- Choosing which extracted fields get persisted, and mapping results to `reports.status` (Sprint 3, US-012/US-014).
- Loading adapters dynamically, or configuring them from the database or the UI: adapters are code (section 5).

## Notes for verification

- AI plugins are a separate system (FR5, section 2.2). Nothing here involves an LLM.
- `field_key` is deliberately not a foreign key to `field_catalog` (data model notes). Keep the adapter's `fieldKeys` as plain strings. US-010 checks that they agree with the seeded catalogue.
- Keep it this small. The only extension point the requirements ask for is "one adapter per report format".
