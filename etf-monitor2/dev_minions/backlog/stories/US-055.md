## User story
As the user, I want to talk to the chat like to a colleague — in Romanian or English, in my own words — so that it turns
what I say into changes in the app, answers back in normal language, and asks me when it is not sure what I mean.

## Context
The user, 2026-10-05: "The AI is very dumb, no natural language, I can't have a proper conversation with it." Today
every reply is one of a few fixed template sentences and the model's own words are never shown (DEC-017 sprint-06
decision 7, kept by DEC-025 §5). US-053/054 fix understanding; this story fixes the conversation.

## Product requirements (PO, decided)
1. **Natural reply every time.** Each answer contains a short reply written by the model in the language the user wrote
   in (RO or EN): what it understood and what it did, or what it needs. Plain text only (escaped, never HTML, never
   executed), length cap per DEC-027. Fixed template sentences remain only as fallbacks when there is no usable model
   reply (provider error, timeout, unusable output).
2. **What really happened is always shown by the app.** Under the model's reply, the server-built result list from
   DEC-025 §5 (e.g. "Added: max of Units in circulation over the last 30 days — BTBETRETF, PTENGETF, TVBETETF") and the
   specific failure reasons ("PTENGETF: no custom value matches 'max, units in circulation, 30 days'"). It is visually
   separate from the model's words. If the two disagree, the result list is the truth; the model's reply must not claim
   a change that did not happen (DEC-027 says how).
3. **Memory: the last 21 messages** of the visible conversation (user + assistant, counted one by one) go with each
   request, so "and for 30 days too", "remove that", "the second one", "da" work. The conversation lives in the browser
   page; a **"New conversation"** button clears it. Per-message shortening per DEC-027.
4. **Clarifying dialogue.** When a request is ambiguous or misses a detail, the assistant asks one specific question,
   and may offer the options it sees (e.g. "Do you mean the max over 7 days or over 30 days?"). The user's short answer
   completes the original request — they do not have to repeat it. Nothing changes until the request is clear.
5. **Questions about the setup are answered**, without changing anything: which ETFs are active, which fields are
   tracked for an ETF, which custom values exist, which provider/model is in use, and "what can you do?" / "help".
   Answers come only from the data the app gives the model (DEC-025 §1) — never invented.
6. **Out-of-scope requests** get a natural answer that says what the assistant can do instead (no template).
7. **Longer messages:** one user message can be up to **2000 characters** (today 500).
8. **Unchanged safety:** closed set of operations, never code (DEC-022); the user's message and stored data are data,
   not instructions; no key ever in the chat (key-request refusal unchanged); model text is never executed or rendered
   as HTML; sanitised logs.

## Acceptance criteria (PO, 2026-10-05)
- AC1 — Gates: typecheck, lint, build, full test suite and `scripts/claude/predeploy-check.sh` pass; no existing
  behaviour test is loosened (AGENTS.md); deliberate test changes are listed in HANDOVER with the reason.
- AC2 — Natural reply: with recorded model outputs, a successful request shows the model's reply (RO for a Romanian
  message, EN for an English one) plus the server-built result list; an injected `<script>` or HTML in the reply renders
  as text; a reply over the cap is cut — tests.
- AC3 — Truth: when the model's reply says something was done but validation or execution failed, the result list shows
  the failure and the UI does not present the change as done — test.
- AC4 — Memory: 21 messages are sent (the 22nd oldest is dropped); per-message shortening applies; "New conversation"
  empties what is sent next — tests.
- AC5 — Clarifying dialogue: (a) an ambiguous request yields a question and changes nothing; (b) the user's short answer
  ("30 de zile", "the second one") produces the intended actions using the remembered request — recorded-output tests.
- AC6 — Setup questions: "ce câmpuri urmăresc la PTENGETF?", "which custom values do I have?", "what can you do?" get an
  answer and no action is executed — tests.
- AC7 — A 2000-character message is accepted, a 2001-character one is refused with the existing "too long" reason — tests.
- AC8 — Conversation regression suite: at least 10 scripted multi-turn dialogues (RO and EN) with recorded model outputs,
  including the user's 2026-10-05 transcript replayed as one conversation, each asserting the actions run and the
  result list shown — tests (no network).
- AC9 — Key-request refusal, "message is data" rule and closed operation set unchanged; boundary tests green.

## For the user (manual check on the live app, after deploy — goes into the demo file)
Pick a strong model first (e.g. Groq `openai/gpt-oss-120b`, Gemini `gemini-2.5-flash`) and press "Test connection".
Then, in one conversation:
1. "ce poți face?" → a natural answer listing what it can do.
2. "adaugă maximul unităților în circulație pe ultima săptămână" → added to all active ETFs, reply + result list.
3. "și pe 30 de zile" → the same for 30 days, without repeating the field.
4. "șterge-l pe cel de 7 zile doar la PTENGETF" → cleared on PTENGETF only.
5. "clear the min" (when there is none / more than one) → a question, nothing changed; answer it.
6. "which custom values do I have on TVBETETF?" → an answer, nothing changed.
Say "accept US-055" or what felt wrong.

## Out of scope
Confirmation before big changes, self-correction and structured output (US-058). Questions about the data values
(e.g. "what was the NAV of TVBETETF last Friday?") — a possible later story. New widget operations, code generated by the
model, keys in chat.
