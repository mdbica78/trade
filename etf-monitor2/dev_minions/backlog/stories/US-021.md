# US-021 — Admin: tracked-field management per ETF
> Detailed by agent (story-planner), 2026-09-26 — PO to confirm at demo.

**Sprint:** 5 · **Epic:** EPIC-05 · **Depends on:** US-020
**Suggested model / thinking:** mid model, medium thinking. Complex (DB writes to the rows that drive the home-table columns and the daily job, 9 ACs), so it is planned by `story-planner`.

## Context

FR10: "Parameter management: per ETF (or per adapter/report type), which fields are available for extraction and which of them are active/tracked." FR2 is the same choice made by chat (Sprint 6). FR7: the home-table columns are "the parameters the user has chosen to see (not fixed — configurable)".

What exists:
- `field_catalog` (data model): what each adapter can extract, per `adapter_key`, with `label_ro`/`label_en` and `unit`. The seed fills it for `brd-depositary` (8 fields). The adapter's own `fieldKeys` are in code (`lib/extraction/adapters/brd-depositary.ts`).
- `tracked_fields` (data model): `(etf_id, field_key)` unique, `display_order` = "column order on the home table". `field_key` is a plain string, not a foreign key, "so historical values survive a catalogue change".
- **Carry-forward note:** these rows drive the home-table columns. Columns are the **union** of the active ETFs' tracked fields, ordered by the **lowest** `display_order` any ETF gives the field, then `field_key` (Sprint 4 decision 3, `lib/monitoring/home.ts`). `display_order` is per ETF, the columns are shared.
- The daily job persists only tracked fields (US-012 AC3, PRODUCT P1 literal reading). A tracked field the adapter cannot extract makes the extraction incomplete, so the report is stored as `parse_error` (US-012 AC3, US-014).
- US-020 provides the admin shell, the ETF list and the `lib/config/` pattern (plain functions over `Db` + `BatchRunner`, Server Actions as thin wrappers). It also lets the admin change an ETF's adapter, which can leave tracked fields the new adapter cannot extract.

## Task

1. **Configuration layer**, `lib/config/tracked-fields.ts`, same rules as `lib/config/etfs.ts` (no Next.js imports, injected runner, typed results; the Sprint 6 chat reuses it):
   - `listFieldsForEtf(symbol)`: the ETF, its adapter state, and one entry per **available** field (sprint decision 7: catalogue rows for the ETF's `adapter_key` whose `field_key` is in the registered adapter's `fieldKeys`), with labels, unit, `tracked` and, if tracked, its position. It also returns every tracked field that is **not** available, flagged;
   - `trackField(symbol, fieldKey)`: only an available field. Inserts one `tracked_fields` row placed last for that ETF (decision 8). Already tracked → no-op success;
   - `untrackField(symbol, fieldKey)`: deletes the row, available or not. Deletes nothing else;
   - `moveField(symbol, fieldKey, "up" | "down")` (or an equivalent explicit-position operation, the plan's call): changes that ETF's order. The ETF's `display_order` values are rewritten in **one** `BatchRunner` call, so a failure never leaves a half-renumbered list (DEC-010: no interactive transactions on neon-http).
2. **Page**, e.g. `app/admin/etfs/[symbol]/fields/page.tsx`, linked from each row of US-020's ETF list. It shows the ETF's available fields with the catalogue label for the locale and the unit, tracked state, the ETF's order, and track / untrack / move controls. Also:
   - flagged not-available tracked fields, with only an untrack control and a translated note that the daily extraction for this ETF records an error while such a field is tracked (US-012 AC3);
   - an ETF with no available adapter: a translated "extraction unavailable, no fields to choose" message (section 3);
   - one translated sentence explaining the shared column order (decision 8);
   - one translated sentence saying a newly tracked field has values from the next daily run on (P1 literal reading, FR4.2 "no backfill").

   Server Actions are as in US-020: no SQL, no exception text, revalidate `/`, `/etf/<symbol>` and the page.
3. **Messages:** new `Admin.*` keys in both catalogues.
4. **Tests:** PGlite tests for every function, **plus** tests that run the shipped home-table loader and ingestion loader statements after a change. Render tests in `ro` and `en`. Action tests with the config layer mocked.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1** — Available vs tracked. For a `brd-depositary` ETF, the page lists the eight catalogue fields with the locale's label and unit, and marks exactly the tracked ones. The list is the intersection of `field_catalog` for the ETF's `adapter_key` and the registered adapter's `fieldKeys`. A catalogue row whose `field_key` the adapter does not declare is not offered. A test covers that case. (FR10 "which fields are available for extraction and which of them are active/tracked"; data model `field_catalog`; decision 7)
- **AC2** — Track. `trackField` on an available field inserts exactly one `tracked_fields` row for that ETF, with a `display_order` greater than every other of that ETF's rows. Tracking an already tracked field changes nothing. Tracking a field that is not available for the ETF (another adapter's key, an unknown key, or any key for an ETF without an available adapter) returns an error and writes nothing. (FR10; FR2; US-012 AC3 "a tracked field … unknown to the adapter makes the extraction incomplete"; decision 7)
- **AC3** — Untrack keeps history. `untrackField` deletes that one `tracked_fields` row. `report_values` and `reports` are unchanged: a PGlite test stores a report with values for the field, untracks it, and finds the same rows. A flagged not-available tracked field can be untracked. (FR10; data model note "`field_key` is a plain string … so historical values survive"; FR4)
- **AC4** — Order. Moving a field changes only that ETF's `display_order` values, in one `BatchRunner` call. The resulting order is strict and gap-free for that ETF. Moving the first field up, or the last down, changes nothing. A test with a failing runner shows the ETF's order unchanged after the failure. (Data model `tracked_fields.display_order` "column order on the home table"; FR7 "configurable"; DEC-010; decision 8)
- **AC5** — Home table follows. After `trackField`, `untrackField` and `moveField`, a PGlite test runs the **shipped** home-table loader (`lib/monitoring/home.ts`) and checks its columns against Sprint 4 decision 3. The column appears when one active ETF tracks the field, disappears when none does, and is placed by the lowest `display_order` any active ETF gives it. One case has two ETFs giving the same field different positions. No code changes between the reads. (FR7 "Dynamic columns … configurable"; Sprint 4 decision 3; carry-forward note)
- **AC6** — Daily job follows. After the same changes, the shipped ingestion loader (`lib/ingestion/load-etfs.ts`) returns the ETF's new `trackedFieldKeys`, in the new order. (FR3 "extracts the selected parameters"; FR2; US-012 AC3)
- **AC7** — No adapter. For an ETF whose `adapter_key` is NULL or not registered, the page shows the translated "extraction unavailable" message and offers no field to track. Its existing tracked fields, if any, are listed flagged and can be removed. (Section 3 "automatic extraction is marked 'unavailable'"; FR13; decision 7)
- **AC8** — Bilingual and failure states. Every string goes through next-intl with keys in both catalogues, and the key-parity test passes. Render tests in `ro` and `en` show the locale's field labels (from `field_catalog`) and messages. An unknown symbol gives a 404. A database error gives a translated message with no exception text. A failing write action returns a translated error with no exception text. (FR8.1; AGENTS.md secrets rule; US-020 AC9 pattern)
- **AC9** — Boundaries and gates. `lib/config/tracked-fields.ts` imports nothing from `next/*`, React or `app/`. No test connects to Neon. `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` (with `DATABASE_URL` unset) pass. (FR9 "same configuration model"; AGENTS.md Commands, "Tests never call live Neon")

## Out of scope

- A global column order across ETFs, or a live preview of the home-table header (decision 8).
- Editing `field_catalog` labels or units. The catalogue describes the adapters, which are code (requirements §5).
- Backfilling values for a newly tracked field (FR4.2). Storing every extracted field is PRODUCT P1 (US-012), not this story.
- Reconciling column labels when two adapters share a `field_key` (Sprint 7, Sprint 4 audit N3). This page uses the ETF's own adapter's labels, like the history page.
- Schema changes. None are needed.

## Decisions needed

Listed in `backlog/sprints/sprint-05.md` → "Decisions needed":
- #7 TECHNICAL — "available" = catalogue for the ETF's adapter ∩ the registered adapter's `fieldKeys`; not-available tracked fields flagged and removable only.
- #8 PRODUCT — order stays per ETF (data model), and a new field goes last. Default shipped in `lib/config/tracked-fields.ts`, with one explanatory sentence on the page.

## Notes for verification

- AC5 and AC6 must execute the **same** statements the home page and the cron use (`buildActiveEtfsStatement` in `lib/monitoring/home.ts`, `buildLoadActiveEtfsStatement` in `lib/ingestion/load-etfs.ts`), not a copy of their SQL. That is what "no code change between the reads" proves.
- `trackField` placing the field "last" should be computed inside the insert statement (e.g. `coalesce(max(display_order), -1) + 1` in a subquery), not read in one call and written in another, so two quick clicks cannot produce equal positions. If the plan relies on renumbering instead, it says so.
- Under P1's literal reading, a field tracked today has no stored value until the next daily run. The home-table cell is empty (`tracked: true, value: null`, US-016 AC2). That is correct, not a bug.
