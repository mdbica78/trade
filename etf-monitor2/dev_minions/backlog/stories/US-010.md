# US-010 — BRD depositary adapter (units in circulation, net asset, VUAN, investor counts)
> Detailed by agent (story-planner), 2026-09-23 — PO to confirm at demo.

**Sprint:** 2 · **Epic:** EPIC-02 · **Depends on:** US-009
**Suggested model / thinking:** strong model, high thinking. Complex (adapter framework, 10 ACs), so it is planned by `story-planner`.

## Context

BTBETRETF, TVBETETF and PTENGETF share one report template, from the depositary BRD — Groupe Société Générale (requirements section 3). US-005 seeded them with `adapter_key = 'brd-depositary'`, along with the eight catalogue fields this adapter must produce. The US-001 spike (`spikes/pdf-extraction/FINDINGS.md`) documents the text `unpdf` returns for these reports, the number format, and three traps. This story encodes those findings as a deterministic parser (FR5), implementing the US-009 contract.

The adapter receives the text from US-008's `extractPdfText` (flattened, single-spaced) and nothing else.

## Task

1. Implement the `brd-depositary` adapter, e.g. `lib/extraction/adapters/brd-depositary.ts`, and add it to the default registry (US-009).
2. **Field rules** (field keys from `lib/db/seed-data.ts`; labels from FINDINGS / US-001). Match labels, not page positions (section 3). The one exception is VUAN, where FINDINGS documents a positional rule.

   | field_key | Rule |
   |---|---|
   | `net_asset` | The number right after `ACTIV NET (in valuta fond - RON)`. Not the `ACTIV NET (in valuta clasa UF - RON)` line, which precedes it, and never a fallback to it when the "fond" label is absent. |
   | `units_in_circulation` | The number right after `NUMAR U.F. in circulatie, din care detinute de:` |
   | `units_held_individuals` | The number after the first `Persoane fizice` that follows the `NUMAR U.F.` label **and precedes `Numar investitori, din care:`** (to the end of the text if that label is absent). Never the investors block's `Persoane fizice`. |
   | `units_held_legal_entities` | The number after the first `Persoane juridice` that follows the `NUMAR U.F.` label **and precedes `Numar investitori, din care:`** (same bound). Never the investors block's `Persoane juridice`. |
   | `nav_per_unit` | FINDINGS trap 1: the value sits before its label. Take the single number token between the `units_held_legal_entities` value and `Numar investitori, din care:`. Accept it only if the label `VALOARE UNITARA A ACTIVULUI NET (VUAN)` is present somewhere in the text and exactly one number sits in that gap. Otherwise the field is missing. |
   | `investors_total` | The number right after `Numar investitori, din care:` |
   | `investors_individuals` | The number after the first `Persoane fizice` that follows the `Numar investitori` label |
   | `investors_legal_entities` | The number after the first `Persoane juridice` that follows the `Numar investitori` label |

   Label matching should tolerate runs of whitespace. Beyond that, labels are matched as documented.
3. **Report date** (FINDINGS trap 2): take `DD.MM.YYYY` from `Raport depozitar la data de DD.MM.YYYY` and return it as `YYYY-MM-DD`. Never use the BVB filing stamp near the top (`NNNNN/DD.MM.YYYY`), which is one day later. If that footer phrase is not found, or the date is not a real calendar date, the result is `ok: false`.
4. **Number parsing** (FINDINGS "Number formatting (AC5)"):
   - comma is the thousands separator and dot the decimal separator; the number of decimals varies;
   - accept either correctly grouped digits (`\d{1,3}(,\d{3})+`) or plain digits, each optionally followed by `.digits`;
   - the canonical `numericValue` is the token without commas, with its decimals kept as written (`8,640,000.00` → `8640000.00`);
   - anything else (`1.234,56`, `12,34`, `1,2345`, text) is not a number. The field goes to `missingFields`; nothing is guessed.

   Put the parser in its own small module with its own tests, e.g. `lib/extraction/numbers.ts`, so a later adapter can reuse it or deliberately not.
5. **`canHandle(text)`** is true only when the text contains `Raport depozitar la data de`, `NUMAR U.F. in circulatie` and `VALOARE UNITARA A ACTIVULUI NET (VUAN)`.
6. **Unit tests on text**, not PDFs. Build strings in `unpdf`'s flattened format, modelled on the BTBETRETF excerpt in FINDINGS, plus variants for each edge case. The PDF-fixture regression suite is US-011.

## Acceptance criteria

- **AC1** — The adapter's `key` is `brd-depositary`. Its `fieldKeys` equal exactly the set of `fieldKey`s that `seedFieldCatalog` (`lib/db/seed-data.ts`) lists for `brd-depositary`. A test asserts this, so the catalogue and the adapter cannot drift apart. (FR10; data model `field_catalog` "what each adapter can extract"; US-005)
- **AC2** — The default registry returns this adapter for `get("brd-depositary")`, and every `adapterKey` in `seedEtfs` resolves to a registered adapter. (Section 3; US-005 seed)
- **AC3** — Given text containing both the filing stamp `16426/22.09.2026` and the footer `Raport depozitar la data de 21.09.2026 in valuta RON`, `reportDate` is `2026-09-21`. Text without the footer phrase gives `ok: false`. (FINDINGS trap 2; data model `reports.report_date` "the date the report is for")
- **AC4** — On a text modelled on the BTBETRETF excerpt in FINDINGS, the adapter returns:
  - `net_asset` = `415591664.27` (not taken from the "clasa UF" line; the test uses a variant where the two lines differ);
  - `units_in_circulation` = `37470000`, `units_held_individuals` = `29733778`, `units_held_legal_entities` = `7736222`;
  - `investors_total` = `18708`, `investors_individuals` = `18631`, `investors_legal_entities` = `77`;
  - each with its verbatim `rawValue` (e.g. `415,591,664.27`).

  The two `Persoane fizice`/`Persoane juridice` pairs are told apart by their parent label. (FR3; FINDINGS trap 3; section 3 "field labels")
- **AC5** — `nav_per_unit` = `11.091` from the positional rule. It is missing, with nothing guessed, when (a) the VUAN label is absent from the text, (b) the gap holds no number, or (c) the gap holds more than one number. (FINDINGS trap 1; AGENTS.md "Never guess a value")
- **AC6** — The number parser maps:
  - `37,470,000` → `37470000`
  - `8,640,000.00` → `8640000.00`
  - `415,591,664.27` → `415591664.27`
  - `1,517,663,423.87` → `1517663423.87`
  - `11.091` → `11.091`
  - `54.1373` → `54.1373`
  - `77` → `77`

  It rejects `1.234,56`, `12,34`, `1,2345` and a non-numeric token. In the adapter, a field whose token is rejected is listed in `missingFields` and has no value. (FINDINGS "Number formatting (AC5)"; data model `raw_value`; AGENTS.md "Never guess a value")
- **AC7** — Removing one label from the text makes the fields anchored to it missing, never shifts a value from another block into them, and leaves every other field returned with its correct value. One test per case:
  - `ACTIV NET (in valuta fond - RON)` removed → only `net_asset` is missing (the "clasa UF" value is not used);
  - the units block's `Persoane fizice` removed → only `units_held_individuals` is missing (the investors block's `18,631` is not used);
  - the units block's `Persoane juridice` removed → `units_held_legal_entities` and `nav_per_unit` are missing (the VUAN gap starts at that value; the investors block's `77` is not used);
  - `NUMAR U.F. in circulatie, din care detinute de:` removed → the three `units_*` fields and `nav_per_unit` are missing;
  - `Numar investitori, din care:` removed → the three `investors_*` fields and `nav_per_unit` are missing; the `units_*` fields are still correct;
  - the investors block's `Persoane fizice` or `Persoane juridice` removed → only that investors field is missing.

  (Section 3; FR4.1 spirit: blank, not invented; AGENTS.md "Never guess a value")
- **AC8** — `canHandle` is true for the BRD-format text and false for unrelated text (for example, a text using `VAN` instead of `VUAN`, like ICBETNETF's format). Every result the adapter returns in these tests has no violations under US-009's `validateExtractionResult`. (Section 3; US-009 contract)
- **AC9** — The adapter is a pure function of its input text: no LLM/AI, network, database or PDF-library import. Checked by review. (FR5; AGENTS.md "PDF extraction is a classic deterministic parser, never AI")
- **AC10** — `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass. (AGENTS.md Commands)

## Notes for verification

- `architecture/data-model.md` says in its notes that the reports use `.` as a thousands separator. That contradicts the spike, which measured `,` thousands / `.` decimal on all three fixtures (Sprint 1 audit N6). **Follow FINDINGS.** The data-model note is for the Technical Lead/PO to correct. This story does not edit architecture docs.
- The rules above come from three reports of a single date. US-011's fixture suite is the proof that they hold on real PDFs. If a real fixture contradicts a rule, fix the rule and note it in the plan. Do not special-case the fixture.
- Reviewer: check that no rule reads a fixed character offset or a fixed token index counted from the start of the document. Every value must be anchored to a label, or to the documented VUAN gap.

## Tech-lead review 2026-09-23
Sprint review (tech-lead subagent, in-loop, DEC-009). Fixed in place, no product choice involved:
- **Task 2 / AC7 were inconsistent.** The original AC7 ("remove any one label → only that field is missing, every other field still returned") cannot hold under the Task 2 rules: removing a parent label (`NUMAR U.F. …`, `Numar investitori …`) also removes the anchor of its two sub-fields and of the VUAN gap. Worse, the original sub-label rule ("the first `Persoane fizice` that follows the `NUMAR U.F.` label") was unbounded: with the units block's `Persoane fizice` missing it would silently pick the investors block's value (`18,631`), which is a guessed value. The units sub-labels are now bounded by `Numar investitori, din care:`, `net_asset` explicitly never falls back to the "clasa UF" line, and AC7 lists the exact dependent fields per removed label.
- Verified the rules against `unpdf` 0.11.0 output of all three committed fixtures (BTBETRETF, TVBETETF, PTENGETF 2026-09-21): every label is present, the VUAN gap holds exactly one number in each (`11.091`, `54.1373`, `14.8856`), and both "din care" breakdowns sum exactly.
