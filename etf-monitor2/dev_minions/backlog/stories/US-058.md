# US-058 — Assistant reliability: confirm before big changes, self-correction, structured output
> Written by the PO with the user, 2026-10-05 (`backlog/sprints/sprint-13.md` → "PO review"). Binding text: **DEC-027**
> (conversational assistant). Product requirements below are decided; the technical design is DEC-027's.

**Sprint:** 13 · **Epic:** EPIC-08 · **Depends on:** US-055 (build order US-053 → US-054 → US-056 → US-057 → US-055 → US-058)
**Suggested model / thinking:** strong model, high thinking (AI capability system) → `story-planner` plan.

## User story
As the user, I want the assistant to get my request right the first time more often, and to check with me before it
removes or clears things across several ETFs, so that I can trust it with plain-language instructions.

## Product requirements (PO, decided)
1. **Confirm before big changes (default).** Before running any of: remove an ETF; stop tracking a field; clear or
   replace custom values on **more than one** ETF — the assistant shows the plan in plain words, with the server-built
   list of every change and ETF, and asks "Proceed? / Continui?". It runs only after the user agrees ("da", "yes", "ok",
   "go ahead" …); anything else cancels or is treated as a new request. Adding ETFs/fields/custom values and edits on a
   single ETF run immediately. A message containing both kinds waits for confirmation as a whole.
2. **What runs is what was shown.** After "yes", exactly the validated plan shown is executed — not a new
   interpretation by the model. A plan expires (DEC-027 sets how long) and is refused if the data changed so that it no
   longer validates; the user is told why.
3. **Self-correction.** When the model's actions fail strict validation, the server sends the specific reasons back to
   the model once and validates its corrected answer before replying. The user sees only the final outcome. Cap on model
   calls per user message per DEC-027 (PO suggests 2, at most 3).
4. **Structured output where available.** Use the provider's native tool/function calling or JSON-schema output when it
   supports it, falling back to today's JSON-in-text; the choice per provider is DEC-027's. Works the same for presets
   and custom providers.
5. **Unchanged safety** as US-055 requirement 8.

## Acceptance criteria (PO, 2026-10-05)
- AC1 — Gates: typecheck, lint, build, full test suite and `scripts/claude/predeploy-check.sh` pass; no existing
  behaviour test is loosened (AGENTS.md); deliberate test changes are listed in HANDOVER with the reason.
- AC2 — Each confirm-category action (remove ETF, untrack, clear/replace on 2+ ETFs) is not executed on the first turn;
  the plan is shown; "da"/"yes" executes it; "nu"/"no" executes nothing; a single-ETF clear and any add run at once — tests.
- AC3 — After "yes" the executed actions equal the shown plan even if the model would now answer differently; a tampered,
  expired or no-longer-valid plan is refused with a specific reason — tests.
- AC4 — Self-correction: a recorded first answer that fails validation followed by a valid corrected answer produces the
  correct actions and one reply; model calls never exceed the DEC-027 cap; a second failure ends with the specific
  reason — tests with fake fetch.
- AC5 — Structured output: for each provider family the request uses the mode DEC-027 chose, and the fallback path works
  when the provider rejects it — tests with fake fetch, no network.
- AC6 — Key boundary, sanitised logs, closed operation set unchanged; boundary tests green.
