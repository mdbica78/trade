# US-044 — Widget engine and history-area rendering
> Detailed by agent (story-planner), 2026-10-02 — PO to confirm at demo.

**Sprint:** 11 · **Epic:** EPIC-08 · **Depends on:** US-043
**Suggested model / thinking:** strong model, high thinking. Complex (pure exact-arithmetic engine,
history-query integration, optional-table behavior and bilingual detail-page UI).

## Context

FR18 requires configured derived values to persist and appear in the ETF detail page. DEC-022 §§2
and 8 settle calculation semantics, exact arithmetic, basis dates, localized fallback and the
optional display area. The approved Sprint 11 review requires a pure engine, catalogue-only field
definitions, sanitized errors, and explicit coverage of calendar gaps and missing data. Historical
reports may lack fields that were not stored when they were ingested; do not backfill or infer them.

## Task

Implement a pure deterministic widget engine using the existing exact decimal/bigint helpers and a
detail-page read/render path for the optional “Custom values” area above the history table. A widget
is evaluated against `ok` reports only. For day periods use the inclusive date window relative to
the newest `ok` report; for report periods use the requested count of newest `ok` reports. Keep the
existing ETF history page usable when `etf_widgets` is absent or its query fails: hide only this
area and emit one sanitized `[load-error]` line through the established DEC-019 helper.

## Acceptance criteria (DRAFTED BY AGENT — PO to confirm)

- **AC1 — Deterministic periods and latest report.** The pure engine uses the newest `ok` report,
  not the calendar date, as “today.” A `days` period uses the inclusive range from latest report
  date minus the requested amount through that latest report; a `reports` period uses the latest
  requested number of `ok` reports. Invalid/non-`ok` rows do not enter either basis. Table-driven
  tests distinguish days from reports and cover weekends/date gaps. (FR18; DEC-022 §2; DEC-022 PW-3)
- **AC2 — Change operations.** `change` and `percent_change` compare the latest field value with
  the newest `ok` report on or before the day-window boundary, or the report-count-earlier value
  for a reports window. A missing field is skipped, never converted to zero. An absent comparison
  value yields `insufficient_history`; a zero divisor yields no percentage result, following P7.
  Tests cover absent comparison reports, missing values, a zero divisor and exact change/percent
  arithmetic. (FR18; DEC-022 §2)
- **AC3 — Aggregate operations.** `average`, `min` and `max` operate only on values present in
  the selected window; missing field values are skipped. An empty value window yields
  `insufficient_history`. Average uses four decimal places, rounded half away from zero; percent
  change uses P7's two decimal places, rounded half away from zero. Tests use exact decimal
  fixtures, including positive and negative rounding boundaries, and contain no floating-point
  approximation. (FR18; DEC-022 §2; DEC-022 PW-2; DEC-007)
- **AC4 — Basis dates.** Every computed result identifies the report date or dates that formed its
  basis: the two reports used for a change comparison and the contributing reports for an
  aggregate. Rendered output includes those dates using the existing report-date formatter for the
  current locale. Pure-engine and rendering tests assert exact basis dates for gaps and weekends.
  (FR18; DEC-022 §§2, 8)
- **AC5 — Detail-page rendering.** When widget definitions are available, the ETF detail page
  renders a translated “Custom values” area above the history table, with each widget's title,
  formatted value, basis dates, and the settled sign/arrow treatment for change values. An
  `insufficient_history` result renders a short translated message, never a guessed numeric zero.
  User-provided titles remain plain text (React-escaped). Render tests cover both Romanian and
  English, change and aggregate presentation, insufficient history, and safe title rendering.
  (FR18; DEC-022 §§1, 8; DEC-007)
- **AC6 — Optional-table and read failures.** If the widget table is absent (`42P01`) or its query
  fails, the Custom values area is hidden, the rest of the ETF detail page/history remains
  available, and exactly one sanitized `[load-error]` diagnostic is emitted through the established
  DEC-019 logging path. Tests cover both missing-table and unrelated query-error cases, assert
  diagnostic sanitization/count, and verify that the page still renders. (FR18; DEC-022 §8;
  DEC-019)
- **AC7 — Scope and regression.** The engine accepts only stored widget definitions whose
  field keys belong to the existing numeric ETF adapter catalogue; it does not add raw fields,
  infer missing values, backfill history, or change PDF extraction. Existing history table and
  chart behavior remains intact. Focused widget/history tests, typecheck, lint, full tests and
  offline build pass without live resources. (FR18–FR19; DEC-022 §§1–2, 9; Sprint 11 review,
  “Historical coverage” and “Extraction boundary”)

## Out of scope

Widget definition persistence/validation (US-043); chat changes (US-045); raw-field support or
extraction changes (US-046 is investigation only); history backfill; new operations; home-table
widgets; live Neon/Vercel/provider calls.

## Notes for verification

Keep calculation code pure and independently testable. Include no-`ok` history, inclusive day
boundaries, report-count boundaries, gaps/weekends, absent comparison, empty aggregate window,
missing fields, zero divisor, negative and positive rounding, and basis dates. Exercise the actual
page/read model in tests for both locales and for the optional-table and sanitized-error paths.
Tests use PGlite or fakes and never access live services or secret-bearing tables.
