## 3. Technical rows settled

**T-1 (US-037): several reports per filing, with the unique key and the budget.**
- Discovery: `parseReportList` already exposes `rowIndex` and `linkIndexInRow`. A new `findLatestFilingLinks` returns **all links of the newest row** (the row `findLatestReportLink` picks today), capped at `MAX_REPORTS_PER_FILING = 4` (Fri + Sat + Sun + one spare; extra links are dropped and the detail says `truncated`). `findLatestReportLink` stays as a wrapper returning the first link, so existing callers and tests keep working.
- Per link: (a) if `reports` already has an `ok` row with this `source_url` for the ETF, skip it with no request (one `source_url = any(...)` query per ETF); (b) otherwise download, extract, take `report_date` from the PDF's own text and write through the existing DEC-010 path — **one batch per report** (report + its values, `ok` last, never downgraded). The unique key `(etf_id, report_date)` makes a repeat harmless; a second link that resolves to a date already stored in the same filing is a no-op.
- Every field: `select-values.ts` stops filtering by tracked keys and returns every extracted value (its own comment names this as the one function PRODUCT decision 1 changes). `report_values.field_key` has no foreign key, so any key the adapter emits is storable. Tracked fields remain the selection for the detail-page charts and history; they no longer decide what is stored.
- ETF outcome: closed codes are unchanged. Priority failure code > `not_attempted` > `ok`; the detail states "stored N, already stored M, failed K, not attempted J".
- Budget (**amends DEC-018 §5**): `MAX_REQUESTS_PER_ETF` becomes `1 + MAX_REPORTS_PER_FILING` (5). `canStartEtf` keeps its meaning but checks the minimum (discovery + one PDF = 2 requests). A new `canStartDownload(now, startedAt)` checks, before every PDF after the first, that `now + CRON_FETCH_TIMEOUT_MS + PARSE_ALLOWANCE_MS <= runDeadlineMs`; if not, the rest are `not_attempted`. `maxDuration = 60`, `CRON_FETCH_TIMEOUT_MS = 7000`, `PARSE_ALLOWANCE_MS = 5000` and `FINISH_RESERVE_MS = 5000` do not change.
- Known limit, stated honestly: a link skipped by the deadline is not fetched by the next daily run (the newest row is a different one). It is fetched by a manual run from `/admin/cron` the same day, and that run downloads only what is missing thanks to (a). PDF fetches normally take about a second, so this should be rare.
- Known limit: reports stored before this sprint hold only their tracked fields. No backfill is built (default; see P-3).

**T-2 (US-036 data rule): "previous available report".** Latest = the newest `ok` report of the ETF. Per field, previous = the newest earlier `ok` report of the same ETF that has a value for that field. `buildPreviousDayOkValuesStatement` changes from `report_date - 1` to "the greatest `report_date` below the latest, for that field"; `computeCellDelta` drops the `previousCalendarDay` comparison. Exact bigint arithmetic and the zero-divisor rule stay. The cell shows the previous report's date in its `title`. Only `home.ts` and `delta.ts` change; the delta unit tests are rewritten for the new rule, deliberately (this is the intent of FR7.2 replacing P6).

**T-3 (US-047): where the home display settings live.** Three new tables in **one migration** (`pnpm db:generate` creates it; an agent must not apply it to Neon; the production deploy applies it, DEC-023; expand-only), all optional for the home page:
- `home_display_settings` — single row (`id = 1`, same pattern as `settings`): `show_absolute`, `show_percent`, `show_arrow` (global change switches), default true.
- `home_display_columns` — `field_key text primary key`, `position integer not null unique`, and nullable `show_absolute`, `show_percent`, `show_arrow` (null = follow the global switch).
- `home_display_etfs` — `etf_id` → `etfs` on delete cascade primary key, `visible boolean not null`. No row means visible.
Why separate tables and not columns on `etfs` or `settings`: Drizzle selects every declared column, so an unapplied migration would break `etfs`/`settings` queries used by the cron, admin and chat. With separate tables the failure is confined to the home display query, which falls back (42P01) like DEC-019. **Independent of tracked fields:** the columns set is the set of field keys in `field_catalog` (labels are identical across adapters, DEC-018 §3), not the tracked union. **Default with nothing saved** = today's table (all active ETFs, tracked union, all change parts on), so the code can ship before the migration and before the user chooses anything. Writes: `lib/config/home-display.ts`, plain functions over `Db` + `BatchRunner` (DEC-016); `saveHomeDisplay` replaces all three tables' rows in one batch; validation as in AC 2. The UI is the home page's Customize panel (spec rule 6): a client component calling one server action per change (`saveHomeDisplay` applies the whole new state in one batch, so two quick clicks cannot leave a half state; the action returns the saved state, which the panel shows); DEC-020 §6 names US-047 for the title row and panel markup only. Chat control of these settings is "later" in FR7.3 and is not in any roadmap story (PO to decide whether to add it).
